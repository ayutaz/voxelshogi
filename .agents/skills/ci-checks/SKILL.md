# CI の確認

- 同じリポジトリの状態取得は最短10分間隔。PR・run・APIを切り替えても間隔をリセットしない。取得をまとめ、直前の結果を再利用する。
- キュー待ちや実行中が続く間は別作業を進める。CI待ちだけで `functions.wait`、`write_stdin`、sleep を短い間隔で繰り返さない。タイマーの満了を細かく取りに行く監視も作らない。
- 他に進められる作業がない場合は、PR URL と未完了チェックを記録して戻る。次の確認が必要になったときに単発で取得する。完了通知が使える場合は通知を優先する。
- 継続が必要な場合は、新しい入力で中断できる10分以上の待機を一度使う。1分刻みのwaitへ分割しない。
- `gh run watch` 等を使う必要がある場合も取得間隔は600秒以上とし、そのプロセスの出力待ちを別の短いwaitループにしない。
- 利用者への報告は状態変更時だけ。実行時間とrunnerのキュー待ちを区別し、待機だけを理由に中断・再実行しない。
- 失敗ログの調査・修正は進めてよい。必須7チェックの欠落・未完了・失敗・中断を成功と見なさず、保護の解除・bypassなしで取り込む。許可済みのmergeも実際の必須チェックがすべて成功してから行う。

`.codex/hooks.json` の SessionStart はこの方針を案内し、PreToolUse は認識できる `gh` の状態取得・短いwatch・CI文脈でのwaitを拒否する。独自のHTTPクライアントや一部のツール経路を完全には制限できないので、スキルの方針も守る。hookの信頼とローカル状態については [開発手順](../../../CONTRIBUTING.md#ci-確認のスキルとhook) を参照。
