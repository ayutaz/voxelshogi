## 棋譜保存の推奨最小構成

まず**Cloudflare Workerの受信API＋D1を1つ**に限定し、棋譜JSONと最小の対局metadataを保存する。
R2・KV・公開対局一覧・ユーザーアカウント・ランキングは初回に追加しない。モデルは既存のHF配布を維持する。
現行のHTML／JS／WASMは引き続きStatic Assetsから配信し、`/api/games`だけを受信Workerへルーティングする。
初回配信の静的アセットとAPI失敗を切り離す。

### 保存内容と利用者への説明（提案値）

- 既定は送信OFF。「対局データを改善調査のため送信する」に同意した対局だけ送る。拒否しても全ゲーム機能を使える。
- 保存対象は標準ルールの棋譜、対局種別、先後のAI条件、モデル／精度形式、アプリcommit、結果・終局／中断理由、受信時刻と同意方針の版。
  名前・メール・HF token・モデル本体・入力フォルダーのpath・ブラウザ操作の全イベントは送らない。
- プロダクトの保存DBへ生IPやUser-Agent全文を入れない設計にする。Cloudflareのアクセスログまで無取得・完全匿名とは説明しない。
- 送信を途中でOFFにした場合、未送信の対局を送らない。ページ離脱時の未送信分を無断でbeacon送信しない。
  初回は手ごとのアップロードをせず、終局または利用者が明示した中断時に1回送る。
- 保持は**30日を初期提案**とし、公開前に用途・保持期間・削除／問い合わせ方法を文書へ確定する。
  公開棋譜一覧、モデル学習への利用、HFへの公開は別の判断とし、この同意へまとめない。

計画の作成は実利用者の収集同意やDB作成・収集開始の代わりではない。
実装・公開を指示された場合も、利用者には送信前に対象と目的を示す。

### 受信・検証・上限

- バージョン付きschema、最大**256KiB／2,048着手**を初期提案とする。上限超過は理由を返し、端末への棋譜保存を妨げない。
  Webの既存4MiB import上限を、サーバーの保存上限と混同しない。
- request IDとpayload hashで再送を冪等化する。同一IDで別本文は拒否し、上書きしない。
- 受信時にschema・サイズ・ruleset・件数・有限値・同意版・rate limitを検証し、最初は`received_unverified`として保存する。
  HTTP成功・クライアント申告の勝敗を、全手合法・検証済み教師の証拠にはしない。
- 全手のRust再生が必要な解析／研究へ渡す場合は、別の外部Linux／GHA検証で`verified`／`rejected`を付ける。
  その実行規模・費用を先に見積もり、停止中のデータ生成・学習・GPUを自動再開しない。
- 初期のアプリ上限案は**受入1,000件/日、保存本文合計100MiB**。到達時は新規収集を止め、対局を継続できるようにする。
  DB全体はindex等で本文より大きくなるため、実使用量も監視する。古いデータの削除も使用量へ計上する。
- 管理用の全件取得・削除は公開APIにせず、既存の所有者認証を使う。初回に無認証の対局一覧を作らない。

上記の値は実装時にschema・境界値テスト・実際の保存量で確定する。
本番には合成したテスト対局だけを使って、送信同意・保持・失敗時の挙動を検証してから有効にする。

### 無料範囲と処理場所

公式仕様の確認日：2026-11-13 JST。
[Workers Free](https://developers.cloudflare.com/workers/platform/limits/)はHTTP CPU10ms・100,000 requests/日であり、
全棋譜のRust再生がこの枠内に入るとは仮定しない。
[D1の制限](https://developers.cloudflare.com/d1/platform/limits/)はFreeの1DB500MB、行／文字列最大2,000,000 bytes。
256KiBはそれより低いアプリ側の提案上限である。
[D1無料枠](https://developers.cloudflare.com/d1/platform/pricing/)は日次5M行読取・100k行書込、全DB合計5GB。
日次上限超過ではqueryが失敗し得るため、収集失敗でゲームを止めない。

現在のアカウントplan・既存サービスと共有する残枠は未確認。これらの公称値をこのサービス専用の空き枠と扱わない。
有料プラン変更、R2購入、GPU予算のWeb費への流用は今回の計画に含めない。
アプリの保存上限だけで、リクエスト数を含むアカウント全体の課金上限まで保証できるとは説明しない。

## 見積もりと判断点

前の「14〜24時間／2〜4作業日」は変更量を実測していない概算であり、納期の根拠として使わない。
まずA・Bで変更量と実作業時間を確認し、残るUI・保存API・動画制作を分けて見積もり直す。
動画は本編15秒・冒頭2候補に範囲を固定する。新規学習や長尺映像を追加しない。
実作業、CIの実行とキュー待ち、実スマホ確保を分けて報告する。
前回の長い自動操作タイムアウトを同じ経路で繰り返さず、短い操作確認で接続を判定してから検証する。

最初の区切りはA＋Bの「初見で観戦でき、別層の着手を追える」版。
Cの保存条件や無料枠が整わない場合は送信OFFを保ち、「棋譜自動保存なし」を明示したAlphaとして紹介する選択を残す。
棋譜収集を紹介の必須条件にする場合は、Cまで終わる前に「対局が蓄積される」と告知しない。
この計画では強い新モデルの完成・全端末対応・Phase7全達成を納期に含めない。
