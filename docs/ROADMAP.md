# ROADMAP / 進捗

最終更新: 2026-10-25

凡例: ✅ 完了・検証済み / 🟡 進行中・一部達成 / ⬜ 未着手

各フェーズは「目的 → ゴール（完了条件） → 作業 → 既知の問題・残りの作業」の順に書く。ゴールは、元の指示書の完了条件に、本プロジェクトで追加した検証条件（TDD・CI など）を加えたもの。フェーズを完了とするのは、ゴールの全項目が ✅ になったときだけとする。

## 全体の目的

9×9×9（729マス・372枚）の三次元将棋を題材に、ルールエンジン・ブラウザゲーム・合成データセット・Transformer モデル・自己対局と分散学習を一貫して公開し、**誰でも再現できる三次元将棋 AI 研究プラットフォーム**を作る（`docs/PROJECT_SPEC.md`）。

## 概要

| Phase | 名前 | 状態 | 目的（一言） |
|---|---|---|---|
| 0 | 調査と設計 | ✅ | 何を・どのルールで・どの技術で作るかを根拠付きで決める |
| 1 | Rust ルールエンジン | ✅ | 全実装が共有する、正しく速いルールの唯一の実装を作る |
| 2 | Web ゲーム Alpha | 🟡 | エンジンを使って、ブラウザで誰でも遊べる最初の版を作る |
| 3 | 合成データセット | ⬜ | 学習の材料となる、検証済みで再現可能なデータを作る |
| 4 | Transformer-S | ⬜ | 学習から Web 推論までの一連の流れを、小型モデルで通す |
| 5 | 自己対局と分散学習 | ⬜ | 教師データなしで強くなる学習ループを、複数 GPU で回す |

| 7 | 正式公開 | ⬜ | 一般ユーザーと研究者が使える形で、すべてを公開する |

## 横断的なゴール（全フェーズ共通）

- すべての実装を TDD で行う。期待値はルール文からの手計算か独立した参照実装で用意し、変異テストで検出力を確認する（ADR-003）。
- GitHub Actions（Public リポジトリのため無料）で、すべてのテストを push / PR ごとに自動実行する。
- 重要な決定は ADR（`docs/ARCHITECTURE_DECISIONS.md`）と本ファイルに記録する。
- 費用が発生する操作は、見積もりを示してユーザーの承認を得てから行う。

## Phase 1: Rust ルールエンジン — ✅

**目的**: Web・Python・探索・学習のすべてが共有する、ルールの唯一の実装を作る。ここに誤りがあると、そのまま学習データとモデルを汚すため、正しさを最優先し、次に速さを確保する。

**ゴール（完了条件）**

| 条件 | 状態 | 根拠 |
|---|---|---|
| Rust 単体テストが通る | ✅ | 80件。CI でも実行 |
| ルール違反の手が拒否される | ✅ | `check_move` / `apply_move` が `MoveError` を返す。打ち歩詰め・二歩・王手放置などをテスト |
| 対局を最後まで進められる | ✅ | ランダム対局を終局まで再生し、全手を参照実装と照合 |
| ルールの仕様がドキュメント化されている | ✅ | `docs/RULESET.md`、`docs/GAME_ENGINE.md` |
| （追加）独立した参照実装と一致し、変異テストで検出力がある | ✅ | 注入した15種類のバグをすべて検出 |

**作業**

- 盤面、座標、駒、初期配置
- 全駒の利き（飛車の長方形遮り、角の台形遮り［10/17 改定版］、竜馬の1歩）
- 合法手生成: 成り（任意・強制）、駒打ち、二歩（層×筋）、行き所のない駒、王手放置の除外、打ち歩詰め
- 終局判定: 詰み、投了、千日手、連続王手の千日手、最大手数
- Zobrist ハッシュ（固定シード、値を固定するテストあり）
- VSFEN、指し手の表記、局面検証（インポート用）、`GameRecord`（`ruleset_id` 付き、再生して検証する）、`Session`（undo/redo/goto）

**テスト**: Rust 80件。参照実装との一致テストは、ランダム盤面1800件の利き、ランダム局面40個、ランダム対局の全手。

**性能**（M1、ネイティブ、release、実測）

- 初期局面の合法手は424手で、生成に1.18 ms
- ランダム自己対局は約1,500手/秒（生成と適用で1手あたり0.66 ms）

**既知の問題・残りの作業**（Phase 1 の完了条件には含めず、後続フェーズで対応する）

- 王手の判定は、盤上の全敵駒に対する総当たり。最適化は、プロファイルを取ってから行う（Phase 3 の探索AIで必要になれば）。
- `apply_move` は合法性を全検証するため遅い。探索用には、検証を省いた高速経路が必要（Phase 3）。
- perft(2) を独立した参照実装で照合する長時間テスト。
- 将棋ったーの公開棋譜による互換性検証（ローカルのみ、`docs/RULESET.md` §9）。

## Phase 3: 合成データセット — ⬜

**目的**: モデルの学習と評価に使う材料を、エンジンから大量に作る。ルールで確定する事実（合法手・王手・詰み）と、探索による推定値（評価値・最善手）を、出所を区別して記録する。誰でも同じシードで同じデータを再生成でき、不正なデータが混ざらないことを保証する。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| 10万局面程度を生成できる | 生成スクリプトの実行ログと件数 |
| データの検証が通る | 検証スクリプト: 全局面の再生、合法手との整合、推奨手が合法手に含まれること、重複検出、不正局面の検出 |
| 同じシードで再現できる | 同じシードで2回生成し、ファイルのハッシュが一致するテスト（CI） |
| Hugging Face に公開できる構成がある | 公開スクリプトと Dataset Card の雛形（`ayousanz/voxelshogi-synthetic-v1`、`ayousanz/voxelshogi-search-v1`） |
| （追加）対局単位で train/val/test が分かれている | 同じ対局の局面が分割をまたがないことのテスト |
| （追加）性能を実測し、費用見積もりを更新している | 探索教師の局面/秒、1試合の CPU 時間を `docs/COST_ESTIMATE.md` に反映 |

**作業**

- 探索AI（Rust）: αβ探索、駒得評価、置換表、検証を省いた高速な指し手適用。Web の Normal 難易度にも使う
- PyO3 + maturin の Python バインディング（`crates/voxelshogi-python`）
- Gymnasium 環境（行動マスク付き）
- Random Self-play、Rules Dataset（合法手・王手・詰み）、Search Dataset（評価値・最善手・ノード数・深さ・時間）
- Parquet で保存し、メタデータ（`ruleset_id`、シード、エンジンの Git コミット、生成アルゴリズムのバージョン）を付ける
- データ検証スクリプト、HF 公開スクリプト、Dataset Card

## Phase 4: Transformer-S — ⬜

**目的**: 盤面を入力に Policy と Value を出す小型 Transformer（5–10M パラメータ）で、「学習 → 評価 → ONNX 変換 → ブラウザ推論 → 対局 UI への組み込み」の一連の流れを最初に通す。本格的な GPU 投資の前に、ブラウザで動くことを確かめる。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| 学習できる | Phase 3 のデータで損失が下がる（小規模はローカル CPU、本番は Vast.ai。承認後） |
| 評価できる | Policy Top-1/Top-k 正解率、交差エントロピー、Value 損失、合法手選択率、Random AI と Search AI に対する勝率 |
| チェックポイントから再開できる | 中断して再開した学習が、中断しない学習と一致するテスト |
| ONNX モデルが Web で推論できる | PyTorch・ONNX Runtime CPU・ORT Web WASM・WebGPU の出力が数値的に一致する。推論時間、メモリ、初回ロード時間を計測 |
| Web 上の人間 vs AI に組み込める | E2E テストで、AI が合法手だけを指して対局を終えられる |

**作業**

- **最優先: ONNX/WebGPU の早期検証**。ランダム重みの小型 Transformer で、変換と推論の可否を確認する。ORT Web の WebGPU 用 wasm（27MiB）が Static Assets の上限（25MiB）を超えるため、R2 配信か軽量ビルドを選ぶ（`docs/TECH_STACK_RESEARCH.md` §3.4）
- 盤面の Tokenizer / Encoder（729トークン＋持ち駒＋手番、手番側の視点）
- Policy Head（from-to アテンション＋成り・打ち）、Value Head（勝ち・引分・負けの3値）
- 教師あり学習、評価スクリプト、ONNX 変換、Web Worker での推論
- HF 公開の準備（`ayousanz/voxelshogi-transformer-s`、Model Card の雛形）

## Phase 5: 自己対局と分散学習 — ⬜

**目的**: 人間や探索AIの教師に頼らず、自己対局で強くなる学習ループを作る。Vast.ai の 1〜4 GPU で、中断しても再開でき、世代ごとの強さを比べられる状態にする。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| 1GPU 学習と 4GPU 学習が動く | DDP で同じ設定の学習が両方で完走する。スループットの比を記録 |
| 自己対局を繰り返せる | 自己対局 → Replay Buffer → 学習 → モデル更新のループが、複数世代まわる |
| 学習を途中から再開できる | インスタンスを止めて別のインスタンスで再開できる（チェックポイントを外部へバックアップ） |
| 各世代の棋力を比較できる | 世代間の対局による Elo などの相対的な強さの指標 |
| （追加）GPU 費用が承認済みの予算内に収まる | 実測した GPU 1時間あたりの学習局面数から見積もりを更新し、承認を得てから実行する |

**作業**

- MCTS、Gumbel AlphaZero 系の探索の検討、KataGo の playout cap randomization
- 自己対局 Actor（Rust の CPU 並列）、Replay Buffer
- DDP、Vast.ai 用の Docker イメージ、チェックポイントの外部バックアップ
- 4GPU での学習検証、棋力評価、`ayousanz/voxelshogi-selfplay-v1` の準備

## Phase 6: Transformer-M と研究比較 — ⬜

**目的**: 本プロジェクトの研究上の中心。729トークンの三次元空間に対し、3D-CNN、Full Attention、Axial Attention、Geometry-Aware Attention を同じ計算予算（FLOPs）で比べ、どの構造が三次元のボードゲームに向くかを示す。良いモデルをブラウザで使える形にする。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| アーキテクチャ間の比較結果がある | 同じ FLOPs での Elo、学習効率、推論速度の表を、再現手順とともに `docs/BENCHMARKS.md` にまとめる |
| Hugging Face にモデルを公開できる | `ayousanz/voxelshogi-transformer-m` と Model Card（ライセンスは公開前にユーザーに確認） |
| Web ブラウザで適切なモデルを選択できる | 端末の性能に応じたモデルの選択、量子化モデル、切り替え時のメモリ解放を E2E で確認 |

**作業**

- Transformer-M（20–35M パラメータ）
- Full / Axial / Geometry-Aware Attention（ヘッドごとの3D相対バイアスか、軸ごとの分解）、3D-CNN のベースライン
- 同じ計算予算での比較実験、推論性能の最適化、ONNX の量子化、モデル公開
