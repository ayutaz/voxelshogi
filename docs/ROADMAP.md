# ROADMAP / 進捗

最終更新: 2026-10-25

凡例: ✅ 完了・検証済み / 🟡 進行中・一部達成 / ⬜ 未着手

各フェーズは「目的 → ゴール（完了条件） → 作業 → 既知の問題・残りの作業」の順に書く。ゴールは、元の指示書の完了条件に、本プロジェクトで追加した検証条件（TDD・CI など）を加えたもの。フェーズを完了とするのは、ゴールの全項目が ✅ になったときだけとする。

## 全体の目的

9×9×9（729マス・372枚）の三次元将棋を題材に、ルールエンジン・ブラウザゲーム・合成データセット・Transformer モデル・自己対局と分散学習を一貫して公開し、**誰でも再現できる三次元将棋 AI 研究プラットフォーム**を作る（`docs/PROJECT_SPEC.md`）。

## 横断的なゴール（全フェーズ共通）

- すべての実装を TDD で行う。期待値はルール文からの手計算か独立した参照実装で用意し、変異テストで検出力を確認する（ADR-003）。
- GitHub Actions（Public リポジトリの標準ランナー）で、main の push / PR ごとにテストを自動実行する。M0 で PR と必須 CI による main 保護を整える。
- 重要な決定は ADR（`docs/ARCHITECTURE_DECISIONS.md`）と本ファイルに記録する。
- 費用が発生する操作は、見積もりを示してユーザーの承認を得てから行う。
- 実装・文書変更の前に必ず作業ブランチを作り、PR と必須 CI を経由する。main への直接 push、force push、削除、保護の bypass は行わない（`CONTRIBUTING.md`）。
- 人間同士の対局・マルチプレイは後続フェーズでも実装しない。対局は人間 vs AI と AI vs AI 観戦に限定する。
- Python は3.14系を基本とし、依存が未対応の場合のみ3.13系を使う。現在は `.python-version` に3.14.9を固定している。

**目的**: Web・Python・探索・学習のすべてが共有する、ルールの唯一の実装を作る。ここに誤りがあると、そのまま学習データとモデルを汚すため、正しさを最優先し、次に速さを確保する。

| 対局を最後まで進められる | ✅ | ランダム対局を終局まで再生し、全手を参照実装と照合 |

| （追加）独立した参照実装と一致し、変異テストで検出力がある | ✅ | 注入した15種類のバグをすべて検出 |

**作業**

- 盤面、座標、駒、初期配置
- 全駒の利き（飛車の長方形遮り、角の台形遮り［10/17 改定版］、竜馬の1歩）

**テスト**: Rust 101件（Phase 1 完了時80件、M0 で検出力を補う21件を追加）。参照実装との一致テストは、ランダム盤面1800件の利き、ランダム局面40個、ランダム対局の全手。

**性能**（M1、ネイティブ、release、実測）

**既知の問題・残りの作業**（Phase 1 の完了条件には含めず、後続フェーズで対応する）

- 王手の判定は、盤上の全敵駒に対する総当たり。最適化は、プロファイルを取ってから行う（Phase 3 の探索AIで必要になれば）。

- perft(2) を独立した参照実装で照合する長時間テスト。
- 将棋ったーの公開棋譜による互換性検証（ローカルのみ、`docs/RULESET.md` §9）。

## Phase 4: Transformer-S — ⬜

**目的**: 盤面を入力に Policy と Value を出す小型 Transformer（5–10M パラメータ）で、「学習 → 評価 → ONNX 変換 → ブラウザ推論 → 対局 UI への組み込み」の一連の流れを最初に通す。本格的な GPU 投資の前に、ブラウザで動くことを確かめる。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| 学習できる | Phase 3 のデータで損失が下がる（小規模はローカル CPU、本番は Vast.ai。承認後） |
| 評価できる | Policy Top-1/Top-k 正解率、交差エントロピー、Value 損失、合法手選択率、Random AI と Search AI に対する勝率 |
| チェックポイントから再開できる | 中断して再開した学習が、中断しない学習と一致するテスト |
| 変換済みモデルが実機の Web で推論できる | 同じ精度形式の基準実装と対応する ORT Web backend の出力を、形式ごとに決めた許容誤差で比較する。対象実機・ブラウザで推論時間、メモリ、初回ロード時間を計測 |
| 量子化・低精度化した版も実際に試せる | Web 向けに作成・評価した実行可能な変換版（FP16・INT8等）を、採用版・比較版ともデモで選択し、対応実機で対局・観戦できる。精度が下がった版も含む。配布ファイルの SHA-256 と評価対象が一致し、各版の精度・棋力・速度・サイズの差を記録する |
| Web 上の人間 vs AI に組み込める | E2E テストで、AI が合法手だけを指して対局を終えられる |

**作業**

- **最優先: ONNX/WebGPU の早期検証**。ランダム重みの小型 Transformer で、変換と推論の可否を確認する。ORT Web の WebGPU 用 wasm（27MiB）が Static Assets の上限（25MiB）を超えるため、R2 配信か軽量ビルドを選ぶ（`docs/TECH_STACK_RESEARCH.md` §3.4）
- 盤面の Tokenizer / Encoder（729トークン＋持ち駒＋手番、手番側の視点）
- Policy Head（from-to アテンション＋成り・打ち）、Value Head（勝ち・引分・負けの3値）
- 教師あり学習、評価スクリプト、ONNX 変換、Web Worker での推論
- 基準モデルと各変換版を同じ評価データ・対局条件で比較し、デモのモデル選択に公開した各版を追加する。精度形式・backend・対応端末を表示する
- HF 公開の準備（`ayousanz/voxelshogi-transformer-s`、Model Card の雛形）

## Phase 5: 自己対局と分散学習 — ⬜

**目的**: 人間や探索AIの教師に頼らず、自己対局で強くなる学習ループを作る。Vast.ai の 1〜4 GPU で、中断しても再開でき、世代ごとの強さを比べられる状態にする。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| 1GPU 学習と 4GPU 学習が動く | DDP で同じ設定の学習が両方で完走する。スループットの比を記録 |
| 自己対局を繰り返せる | 自己対局 → Replay Buffer → 学習 → モデル更新のループが、複数世代まわる |
| 学習を途中から再開できる | インスタンスを止めて別のインスタンスで再開できる（チェックポイントを外部へバックアップ） |
| 各世代の棋力を比較できる | 世代間の対局による Elo などの相対的な強さの指標 |
| （追加）GPU 費用が承認済みの予算内に収まる | 実測した GPU 1時間あたりの学習局面数から見積もりを更新し、承認を得てから実行する |

**作業**

- MCTS、Gumbel AlphaZero 系の探索の検討、KataGo の playout cap randomization
- 自己対局 Actor（Rust の CPU 並列）、Replay Buffer
- DDP、Vast.ai 用の Docker イメージ、チェックポイントの外部バックアップ
- 4GPU での学習検証、棋力評価、`ayousanz/voxelshogi-selfplay-v1` の準備

## Phase 6: Transformer-M と研究比較 — ⬜

**目的**: 本プロジェクトの研究上の中心。729トークンの三次元空間に対し、3D-CNN、Full Attention、Axial Attention、Geometry-Aware Attention を同じ計算予算（FLOPs）で比べ、どの構造が三次元のボードゲームに向くかを示す。良いモデルをブラウザで使える形にする。

**ゴール（完了条件）**

| 条件 | 検証方法 |
|---|---|
| アーキテクチャ間の比較結果がある | 同じ FLOPs での Elo、学習効率、推論速度の表を、再現手順とともに `docs/BENCHMARKS.md` にまとめる |
| Hugging Face にモデルを公開できる | `ayousanz/voxelshogi-transformer-m` と Model Card（ライセンスは公開前にユーザーに確認） |
| Web ブラウザで適切なモデルを選択できる | 端末の性能に応じたモデルの選択、量子化モデル、切り替え時のメモリ解放を E2E で確認 |

**作業**

- Transformer-M（20–35M パラメータ）
- Full / Axial / Geometry-Aware Attention（ヘッドごとの3D相対バイアスか、軸ごとの分解）、3D-CNN のベースライン
- 同じ計算予算での比較実験、推論性能の最適化、ONNX の量子化、モデル公開

### M0: CI/CD と品質基盤

- **目的**: 探索AIなどの実装が増える前に、壊れた変更の取り込み・公開と、依存関係・秘密情報の問題を自動で検出する。
- **ゴール**: PR の必須チェックが取り込みを制御し、テスト済み成果物の本番公開・公開後 E2E・復旧手順まで確認できる。
- **実装順**
  1. CI の再現性と静的検査（Rust/Node 固定、lockfile、Actions SHA 固定、actionlint・ShellCheck・Web lint、結果集約）
  2. 依存関係とセキュリティ（Dependabot、監査、dependency-review、CodeQL、Secret scanning・Push protection、非公開報告・SECURITY.md）
  3. テスト品質の計測（Rust/Web カバレッジ、変異テストの再現。重い検証は週次・手動）
  4. 本番 deploy の直列化・設定漏れ検出・環境 secrets、配信 SHA 確認、公開 E2E と復旧手順
  5. 動作確認済みの必須チェックで main を保護し、PR 運用と CONTRIBUTING.md を整える
- **検証**: 正常な変更が通ることに加え、テスト失敗時に取り込めない、PR から本番公開されない、未配信・配信破損が検出されることを確認する。
- **完了条件と変更ファイル**: [CI/CD 調査と強化計画](CI_CD_PLAN.md) の M0-1〜5 をすべて満たす。GitHub の設定はファイル追加だけで完了扱いにせず、API/UI と実行結果で確認する。
- **費用**: 標準 Ubuntu runner を利用。有料サービスや GPU は追加しない。
- **直近の順序**: [PR #2](https://github.com/ayutaz/voxelshogi/pull/2) の通常取り込みと旧成果物の復旧訓練は完了 → [PR #3](https://github.com/ayutaz/voxelshogi/pull/3) で変異調査の検証不足を補い、全体調査・必須CI・統合後の公開を確認 → M0 の完了判定。forkの実検証は外部からの開発参加時に追加する。M1 の実装にはまだ着手しない。[証拠](M0_VALIDATION.md)

### M1: 探索AI（Rust）

- **目的**: Web の対戦相手と、データセットの教師に使う探索AIを作る。
- **ゴール**: 探索の結果が正しく、固定深さ・固定ノード数などの同じ再現条件なら同じ結果を返す探索AIが、ノード数・深さ・時間の上限付きで使える。実時間上限による停止は別に検証する。
- **作業**
  - 合法性の検証を省いた、探索用の高速な指し手適用
  - αβ探索（反復深化、置換表、手の並べ替え）、駒得評価
- **TDD の順序**（各段階で RED を確認し、最小実装と変異による検出確認を行う）
  1. 高速な指し手適用: 固定 seed のランダム対局の全手で、検証付きの `apply_move` と結果が一致する。
  2. 駒得評価: 手番側の視点で、手計算した期待値と一致する。
  3. αβ探索: 少数駒の局面を使い、テスト側の素朴な全探索（minimax）と深さ1〜3の評価値が一致する。
  4. 戦術: 1手詰めを見つけ、駒を取られる脅威に対応し、必ず合法手を返す。
  5. 高速化: 反復深化・置換表・手の並べ替えの有無で、同じ深さの評価値が一致する。固定した比較局面でノード数削減を確認する。
  6. 上限と再現性: 深さ・ノード数の上限を守り、同じ局面・設定で結果が一致する。時間上限では停止と合法な応答を検証し、実時間だけを同じ手の保証条件にはしない。
- **計測**: 探索のノード/秒を測り、`docs/COST_ESTIMATE.md` に反映する。
- **初期性能の目標**: Normal はまず約1秒で読める深さを測って決める。初期局面は合法手424手、生成約1.18msのため、深い全探索を一律に CI の対象にしない。

### M2: Web で AI と対局

- **目的**: 公開 URL で、人間が探索AIと遊べるようにする。
- **ゴール**: 公開 URL で、人間 vs 探索AI（Normal）が、画面を止めずに遊べる。
- **作業**
  - 探索AIを WASM に追加し、Web Worker で動かす（AI の思考中も画面は止まらない）
  - 難易度を Easy（ランダム）と Normal（探索）にする
  - 思考の中断と、新規対局・undo 後に古い探索結果を適用しない制御
  - JS バンドルを分割して、初回の読み込みを軽くする
- **テスト**（E2E）: AI が合法手で応答する。思考中も画面を操作でき、中断後の古い応答が反映されない。公開 URL でも実行する。

### M3: ブラウザでのモデル推論の検証（Phase 4 の先行作業）

- **目的**: 本格的な学習の前に、Phase 4 の最大のリスク（ブラウザで動くか）を確かめる。
- **ゴール**: 配信方法（R2 か軽量ビルドか）、利用可能な演算子、精度形式ごとの対応 backend・対象実機・検証基準が決まり、ADR に記録されている。公開 URL の技術デモで、変換済みモデルを実機のブラウザで実行できる。
- **作業**
  - ランダム重みの小型 Transformer を作り、ONNX に変換する
  - まず FP32 の変換と出力を検証し、FP16化・量子化を行う場合は各版も対象とする。同じ変換版の基準実装と ORT Web の対応 backend の数値一致を検証し、元の FP32 からの変化とは区別する
  - 対象実機のブラウザで推論時間、メモリ使用量、モデルサイズ、初回ロード時間を測る。精度形式ごとの許容誤差と対応 backend を記録する
  - 公開 URL の技術デモに、作成した実行可能な変換版の選択と実際のロード・推論を用意する。ランダム重みの未学習モデルであることを表示し、棋力の評価は M6 で行う
  - モデルを初めて配信する前に、モデルのライセンスをユーザーと決め、配信記録に残す
- **成果物**: `export/` の変換・数値比較テスト、配信モデルの ID・元 checkpoint・変換設定・SHA-256・opset・runtime の記録、実機結果、公開技術デモ。未対応の実機や backend は理由を示し、別モデルへの差し替えで成功扱いにしない。

### M4: Python バインディングとデータ生成（Phase 3 の本体）

- **目的**: 学習データを、検証済みかつ再現可能な形で作る。
- **ゴール**: Phase 3 のゴールをすべて満たす。
- **作業**
  - PyO3 + maturin で Python バインディングを作る（`crates/voxelshogi-python`）
  - Gymnasium 環境（行動マスク付き）
  - ランダム対局データ、ルールのデータ（合法手・王手・詰み）、探索AIによるデータ（評価値・最善手）を生成する
  - Parquet で保存する
  - データの検証スクリプトを作る
  - 対局単位で train/val/test に分ける
  - Hugging Face への公開スクリプト（dry-run）と Dataset Card の雛形を作る
  - CI に Python のテストを追加する
  - Python 3.14系で依存の解決・ビルド・テストを確認し、未対応がある場合のみ3.13系を使う。切り替え理由を記録する

### M5: 将棋ったー棋譜との互換性検証

- **目的**: 本エンジンが将棋ったーのルールに準拠していることを、実際の棋譜で裏付ける。
- **ゴール**: 取得した棋譜が全手再生でき、終局判定が一致する。不一致がある場合は、その原因が `docs/RULESET.md` §9 に記録されている。
- **作業**
  - 将棋ったーの棋譜表記を、本エンジンの指し手に変換する変換器を作る（テスト付き）
  - 棋譜は gitignore したローカルフォルダに置く。コミットするのは結果だけ

### M6: Transformer-S の学習（Phase 4）

- **目的**: 学習から Web での対局までの流れを、小型モデルで最初に通す。
- **ゴール**: Phase 4 のゴールをすべて満たす。
- **作業**
  - Mac の GPU（MPS）で小規模に学習し、流れを確認する
  - 見積もりを提示して承認を得てから、Vast.ai で本学習を行う
  - 評価、ONNX 変換、Web への組み込み。公開する FP32 / FP16 / 量子化版などは、配信する同じファイルを使って個別に評価する
  - 変換前の基準に対する Policy 精度・Value 誤差・対局勝率の変化と、サイズ・ロード時間・推論時間を記録する。精度低下の有無を測定結果で示す
  - Web 向けに作成・評価した実行可能な全変換版を、採用版・比較版とも公開 URL のモデル選択から人間対AI・AI観戦で実際に操作できるようにする。精度が下がった版も含め、モデル ID・精度形式・実際の backend を表示する
  - 配布ファイルの SHA-256 と評価記録を照合し、対象実機での操作と、各対応 backend の CI/E2E を確認する。WebGPU の実機検証は GPU なし CI の代わりに別途記録する
