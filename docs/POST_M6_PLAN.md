## Phase5：評価・データ・自己対局と分散学習

**目的**：何を改善できたか判定できる評価を整え、自己対局で学習・再開・世代比較を繰り返せるようにする。1GPUで有効性と費用を測ってから複数GPUへ進む。

**フェーズ全体のゴール**：複数世代の自己対局→保存→学習→更新が動き、別実機で再開できる。固定条件で世代とM6／M1を比較し、棋力改善の有無と不確実性を報告する。1GPUと4GPUの学習・再開・スループットも実測する。単にパイプラインが完走しただけで「強くなった」と判定しない。

| 順 | 目的 | 作業・成果物 | 完了条件・次へ進む判断 |
|---|---|---|---|
| P5-0 評価を点検する | 強さの差と打切りの影響を区別する | 現行v1を残し、短い戦術局面・中終盤の合成局面・同じ序盤の先後交換を含む評価v2案。手数上限・探索上限・seed・対局数・区間推定・採否基準を事前固定 | 手計算した勝敗／引分／打切りと独立fixtureで集計・再生・漏洩検出を検証。外部Linuxの少量試行で終局率・対局長・先後差・時間を記録し、評価に感度があるか判断できる |
| P5-1 教師と分布を比較する | データ不足と教師不足を切り分ける | 既存trainに対応する対照と、深い固定深さ／ノード探索・長期対局・中終盤を含む小さい新config。件数、重複、教師の完了深さ、生成／検証／再生成の費用を比較 | valと分布から採用条件を決める。M6 holdoutをtrainへ混ぜず、新configの対局単位splitと最終評価集合を生成前に固定。全検証・再生成一致、Card・license・HF全件hash照合後に本規模へ進む |
| P5-2 1GPU自己対局をつなぐ | 改善ループを最小構成で動かす | Rustの合法手・終局判定を使う探索、policy／valueの利用、Actor、Replay Buffer、学習、モデル更新。まず1方式の探索を選び小規模に実装 | 参照木・手計算した探索例、同点・合法手・終局・上限・中断をTDDで確認。外部Linuxで複数世代を完走し、途中停止→別実機での復旧・継続、履歴とmodel hashの追跡に成功する |
| P5-3 世代を比較する | 模倣精度でなく対局結果を検証する | M6モデル、M1、固定した自己対局各世代を同じ評価契約で比較。旧v1の結果も別枠で保持 | 勝敗・引分・打切り・先後・対局長と不確実性を記録。改善が不明／未達ならそのまま報告し、目的・データを見直す。打切りを引分に変えたり、有利な世代だけを掲載したりしない |
| P5-4 GPU数を増やす | 学習部分の並列化が費用に見合うか測る | CPU CIの小さいDDP検査、外部1→2→4GPU試行。同じglobal batch・データ順序・更新数・精度形式をそろえた比較 | 1GPUと4GPUで学習・保存再開が完走し、実スループット・通信・VRAM・総費用を記録。2GPUは4GPU前の停止判断に使う。4GPU未実測を完了扱いにしない |

### 最初に作るPR

1. **評価契約v2と独立テスト**：打切り別集計、先後交換、対局・局面の識別、固定上限、少数の戦術／終局fixture。M6の評価ファイルを変更しない。
2. **評価の少量試行と用途別の費用制御**：M6用の予算・approvalをPhase5へ流用しない。Phase5の用途・見積もり・ledger・終了経路をCIで検査し、外部試行前に既存承認範囲と一致させる。
3. **教師・長期対局configの試料**：P5-0の結果から比較条件を固定して作る。生成のCPU負荷と全件検証費も測る。
4. **探索とActorの最小ループ**：手書きpolicy／valueを使う参照テストから始め、実モデルの自己対局へつなぐ。Replay Buffer・学習・世代比較はそれぞれレビュー可能なPRに分ける。

まずPR1の仕様・テストをGPUなしで進められる。重い対局・データ生成・実モデル計算はVast.ai／CloudRiftのLinux、回帰検証はCIを使う。Macは編集・読み取り・小さい静的／単体確認のみ。

### 評価・ラベルを混同しない

Policyの訪問回数とValueの出所・尺度は[学習ラベル契約](P5_TARGETS.md)で固定する。
この契約の実装は自己対局・新データ生成・学習の実施を意味しない。

- M6のValueは探索スコアの`tanh(score/1000)`であり、勝率ではない。自己対局の終局結果を教師にする場合は出所・尺度・schemaを明示する。未終局の打切りを自動で引分のValue教師にしない。bootstrap等を使う場合も実終局ラベルと区別する。
- 探索方式（MCTS等）、ノード／推論回数、温度、seed、世代更新条件は実対局前に固定する。候補方式をすべて実装することを先行条件にしない。
- 盤面だけでなく履歴・ruleset・model hashの違いを検査し、探索木や推論cacheの誤流用を防ぐ。ルールをPythonやTypeScriptへ複製しない。
- 新しいモデルの選択・調整にはtrain／valを使う。最終testで教師条件やepochを調整しない。評価v2を作る場合も開発用の局面と最終holdoutを分離する。
- Elo等は十分な終局と比較条件がそろった場合の補助指標とする。全打切りの観測や`[0,0]`のbootstrap区間だけで棋力・勝率を結論付けない。

## Phase6：構造を同条件で比較する

**目的**：729セルの三次元空間に適した構造を、学習量と推論条件の差から分離して調べる。

**ゴール**：Full Attention、Axial Attention、Geometry-Aware Attention、3D-CNNを共通のデータ・評価条件と計算予算で比較し、棋力・教師精度・学習効率・推論速度・容量を再現手順付きで公開する。採用したTransformer-Mと比較用の実行可能な変換版をHFとブラウザへつなぐ。

| 順 | 目的 | 完了条件 |
|---|---|---|
| P6-0 比較条件を固定 | 構造以外の差を管理する | データrevision、split、評価v2、FLOPs算定、更新数、seed数、モデル規模（Mの候補20〜35M）、探索予算と速度／メモリ条件を事前文書化。1回の試行を確定的な研究結論にしない |
| P6-1 少量の演算・費用試行 | 学習前に配布可能性と費用を確認する | 各構造の正しさ・ONNX変換・対象backendの数値照合と、実GPUでの速度／VRAMを測る。M6の学習速度をMモデルや別演算へ外挿しない |
| P6-2 学習・比較 | 同じ条件で研究結果を得る | 固定した複数seed・計算予算で学習と世代／探索比較を完了し、負の結果も含め`docs/BENCHMARKS.md`へまとめる（同ファイルはこの段階で作成） |
| P6-3 配布・観戦 | 比較したモデルを実際に試せるようにする | Model Card、license、HF固定revision・全hash照合、公開catalog、実行可能な低精度版も含む実機観戦と切替・解放・E2Eが成功。対応端末は実測した範囲で表示する |

Phase6の本学習は、Phase5の評価基盤と各構造の少量試行がそろってから見積もる。4GPUが常に安い・速いという前提は置かない。

## Phase7：観戦と研究の入口を仕上げる

**目的**：一般の観戦者が盤面の状況とモデル差を追え、研究者が同じデータ・学習・変換を再現できる公開版にする。

**ゴール**：公開URLで継続観戦・停止・1手送り・速度変更・モデル比較ができ、必要な取得条件が分かる。対象モバイル／低性能端末も実機で検証し、実行可能な表示・backendを選べる。人間対AI、再現手順、公開監視・復旧も確認する。

| 順 | 目的 | 完了条件 |
|---|---|---|
| P7-0 同じ棋譜で表示を比べる | ルール・棋力と演出の効果を分ける | 標準ルールの同じ棋譜・局面で、注目層・捕獲・王手・決着の表示案を比較。勝利条件、両AI、Valueの視点／尺度を説明できる。9王比較室や対人マルチは追加しない |
| P7-1 端末と操作を検証 | 実際に観戦を続けられる範囲を示す | 対象実機ごとの3D／2D・各モデル形式・WebGPU／WASM、操作・中断・長時間観戦を検証。未確保・未測定の端末は対応済みにしない。実行先やモデルを隠して自動置換せず、明示選択と未対応理由を表示する |
| P7-2 公開と再現を完成 | 利用・研究を始めやすくする | HF取得申請→固定revision取得→観戦、外部Linuxでのデータ生成→学習→再開→変換の手順を確認。README・Card・ベンチマーク・license・公開E2E・配信hash・復旧手順が一致する |

観戦導線・説明文・取得手順の整備はPhase5〜6と並行できる。新モデルの実機対応や正式公開の完了判定は、対象モデルと対象端末の証拠がそろってから行う。

## 費用・保存・実行前の判断

2026-10-29の[M6完了時記録](M6_COMPLETION.md#費用と資源終了)では、保守的な予約上限は全体US$61／基本枠100、M6はUS$20／基本枠24。基本枠の未予約分はUS$39だが、サービス残高・請求済み額ではない。実請求は未回収。条件付き追加US$100は未使用。Phase5〜6の[初期費用制御](P5_EXECUTION.md)では、未予約分の内側にPhase5 US$20・Phase6 US$19の上限を置く。新しい実支出・サービス残高ではない。

最初の外部試行は1GPUサーバーでの小規模計測を想定する。M6でのUS$1/時を仮置きした**案**は最大4時間／US$4で、発注済み・現行単価・新規承認を意味しない。起動時に単価・在庫・付属費・必要CPU／RAM・全工程の所要時間を再取得し、既存承認の対象と用途別ledgerを照合する。同目的・承認済み総枠内を毎回の再承認待ちに戻さない。未知の用途・licenseだけを具体化して確認する。

M6と同じSモデル・batch4・教師あり更新を185例/秒、過去単価US$1/時として単純比例した参考値：

| 学習へ投入する延べ例数 | 純更新時間の参考 | 純更新部分だけの参考額 |
|---|---:|---:|
| 10万例 | 約9.0分 | 約US$0.15 |
| 100万例 | 約1.50時間 | 約US$1.50 |
| 1,000万例 | 約15.02時間 | 約US$15.02 |

epoch数は延べ例数へ含める。起動・CPU探索／生成・検証・val・対局評価・変換・HF転送／照合・実機観戦・終了は別途加算する。自己対局の局面数、MCTSの推論回数、MモデルやDDPの費用をこの表から決めない。[費用資料](COST_ESTIMATE.md)の古い市場表は発注単価へ流用しない。

成果物は`voxelshogi/`配下へpublic/manual・Community OFFで公開し、Model／Dataset Card、固定revision、全ファイルhash、復旧可能性を確認する。新IDのlicenseは承認済み対象と照合し、M6の許可を未確定の自己対局データ・Mモデルへ自動流用しない。dataset・学習checkpointをMacへ中継しない。provider APIキーは制御側、必要なHF資格情報は承認済みのSSH標準入力・一時環境／メモリだけで使う。

各PRは作業ブランチ・変更に適した検証・必須8チェックと関連CIの成功・通常mergeを守る。コード変更は独立期待値・変異検出を行い、文書のみなら実装・数値・リンク・コマンドとの照合を行う。CI取得は[ci-checks](../.agents/skills/ci-checks/SKILL.md)に従って最短10分間隔。GPUは終了ガードと費用上限を設定し、成果物を退避・hash照合して所有資源の解放まで確認する。
