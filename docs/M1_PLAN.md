# M1 実装計画: 探索AI（Rust）

更新: 2026-10-26。**未着手**。M0 は取り込み・公開後検証まで完了した（[検証記録](M0_VALIDATION.md)）。本書はこれから実装する内容と完了条件を示す。

## 目的と範囲

Web の Normal 難易度と、後の教師データ生成で共用する CPU 探索を `voxelshogi-core` に作る。まず駒得評価と αβ探索を正しく実装し、固定深さ・固定ノード数で再現できるようにする。WASM の公開 API・Web Worker・難易度 UI は M2、モデル推論は M3、学習は M6 で行う（[全体計画](ROADMAP.md#実行計画マイルストーン)）。

現状は検証付きの `GameState::apply_move` と private な `make_unchecked` がある。後者を含む既存の状態遷移を調べて再利用し、ルールを探索側へ複製しない。公開サイトの相手はランダムAIのままで、探索AIはまだない。

各段階で独立した期待値のテストを先に書き、RED、最小実装、正常系、変異の検出を確認する。[開発手順](../CONTRIBUTING.md) に従って変更前に作業ブランチを作り、段階ごとにレビューできる PR にまとめる。以下の7段階は実装順であり、PR の数や所要時間の確約ではない。

## 実装順と検証

| 順 | 変更する内容 | テスト・完了条件 |
|---|---|---|
| 1 | 合法手を前提にした探索用の適用経路 | 固定 seed のランダム対局の全手で検証付き適用と一致。捕獲・成り・駒打ち・両色・繰り返しの明示局面も含める |
| 2 | 手番側から見た駒得評価 | 盤上・持ち駒・成駒の値を仕様として定義し、手計算と一致。手番反転と両色の対称性も検証 |
| 3 | 最適化前の αβ探索 | テスト側の素朴な minimax と少数駒局面の深さ1〜3で評価値が一致。終局を深さ0の静的評価より先に処理 |
| 4 | 戦術と結果の契約 | 1手詰め、深さ2以上での駒損回避、合法手だけの応答、終局時の手なし、両色の勝敗・引き分けを検証 |
| 5 | 手の並べ替え・反復深化・置換表 | 機能の有無で同じ完了深さの評価値が一致。固定した比較局面でノード数削減を確認し、各機能を切り分けて検証 |
| 6 | 深さ・ノード・時間の上限と再現性 | 予算切れを明示し、未完了の深さを採用しない。固定条件で同じ結果、時間上限で停止して合法に応答 |
| 7 | release 計測と文書更新 | 固定局面でノード/秒・到達深さ・時間・設定を記録し、エンジン文書・ROADMAP・費用見積もりに反映 |

### 1. 状態遷移と 2. 評価

検証を省く適用経路は、同じ局面から生成した合法手だけを渡す内部契約にする。外部入力に対する合法性検証は既存 API で行う。比較では盤面・持ち駒・手番・手数・ハッシュに加え、続く合法手と終局結果も確かめ、千日手・連続王手の履歴が保持されることを確認する。既存適用との比較に加えて、捕獲・成り・駒打ちは手書きの期待値でも検証する。

駒価値の具体値と整数の範囲は段階2で決め、テストの期待値とともに記録する。王の捕獲を評価の代用にしない。終局の勝敗評価は取り得る駒得より優先し、手番側の符号と、早い詰みを優先する場合の距離の扱いを明文化する。

### 3. 参照探索と 4. 戦術

参照 minimax はテスト内で全合法手を素朴に読み、製品の枝刈り・置換表・並べ替えを共有しない。状態遷移には検証付き API を使い、静的評価と終局の期待値には手計算の局面も置く。既存ルールの終局判定を使い、千日手・連続王手を探索側で別解釈しない。呼び出し元が終局済みにした最大手数などの結果も尊重する。

同点手の順序は、移動元・移動先・成り・駒打ちの種別を含む明示的な規則として定義する。`legal_moves` の列挙順はバージョン間の契約ではないため、その順序だけに依存しない。最適化前後はまず評価値で比較し、複数の最善手がある局面では返却手が最善手集合に入ることを確認する。同じ探索設定での再実行は同じ手になることも検証する。

### 5. 最適化と 6. 上限

- 置換表は深さと EXACT / LOWER / UPPER の境界を区別する。浅い値を深い探索の確定値として使わず、中断結果を確定値として保存しない。
- 同じ盤面ハッシュでも千日手・連続王手の履歴が違えば結果が変わり得る。履歴を含むキーや再利用の制限を設計し、異なる履歴を持つ局面で誤った再利用を拒否するテストを置く。手数に依存する制限・詰み距離の値も再利用時に整合させる。
- 反復深化は最後に完了した深さの結果を採用する。深さ0・ノード0などで未探索でも、非終局なら明示した順序による合法な代替手を返す。終局なら手なしとする。ノード数の定義、上限を数える位置、停止理由を API と文書に揃える。
- 再現条件はエンジンコミット・局面と履歴・評価設定・探索設定・置換表の初期状態を含める。固定深さ/ノードのテストと、時計に依存する停止テストを分ける。時間だけを同じにしても環境負荷で到達深さが変わるため、同じ手は保証しない。
- ノード削減は効果の出る固定局面で確認する。反復深化の浅い反復や並べ替えには追加処理があるため、すべての局面・機能で総ノード数が必ず減るとは扱わない。最終深さと反復全体のノード数を分けて記録する。

## CI と計測

各 PR で変更に関連する Rust テスト・fmt・Clippy を実行し、必須7チェックの成功後に取り込む。PR CI は小さな固定局面を使い、約1秒で特定深さへ到達することを一律の合否条件にしない。追加テストには、そのバグを注入したときに失敗する証拠を残す。core の探索実装を全体変異調査にも含め、既存ファイルを変更した場合は同値変異のソース指紋と根拠を再確認する。全体調査の結果・未分類の生き残りを確認して M1 を閉じる。

既存の初期局面424合法手・生成1.18ms・ランダム対局約1,500手/秒は **Apple M1 CPU の2026-10-25実測**で、探索ノード/秒ではない。探索は未計測のため、深さの実用上限や完了時刻はまだ確定しない。

段階7では CPU・OS・Rust版・エンジンコミット、局面と履歴、深さ/ノード/時間上限、置換表と並べ替えの設定、ノード数・完了深さ・経過時間・ノード/秒を保存する。正しさのテストと性能計測を分け、最適化の比較には同じ条件を使う。Normal の約1秒の予算はまず目安として測り、M2 で対象ブラウザの WASM/Worker でも再計測して決める。

M1 の CPU 計測は M4 のデータ生成時間の見積もりに使う。GPU の学習費用は M6 の学習スループットで見積もり直す（[費用見積もり](COST_ESTIMATE.md)）。M1 で有料 GPU は使わない。
