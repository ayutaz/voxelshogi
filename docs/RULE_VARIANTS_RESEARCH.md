# 9層同一配置・複数王ルールの比較調査

調査日: 2026-10-26（JST）。状態: **検討資料。候補ルールは未採用・未実装**。

## 目的と調査のゴール

**目的**: 「通常将棋の配置を9層に並べ、各陣営が9枚の王を持ち、王の獲得数で競う」案について、分かりやすさ・終局条件・既存事例・AI開発への影響を比較し、次に検証する案を選べるようにする。

**今回のゴール**: 一次資料で確認した事実、現行コードと初期配置から確認した値、設計上の推論、未実施の対局検証を区別して記録する。新ルールの採用や対局上の優位性を、調査だけで確定したことにはしない。

## 調査結果と提案

遊ぶ人に「同じ配置が9層ある」「あと何枚の王を取ればよいか」を示す設計を検討するなら、**9層同一配置・各9王・王手なし・相手の王を5枚先取**を最初の試作候補とする。5という値は9枚の過半数で説明しやすい設計上の出発点であり、面白さ・先後の公平さ・適切な対局時間が実証された値ではない。

研究と既存棋譜との比較では、現行の1王ルールを基準にする。現行の `voxelshogi-standard-v1` は変更せず、候補を採用する場合は別の `ruleset_id` を与える。初期配置・勝敗・教師ラベルが変わるため、同じルールとして棋譜・学習データ・モデルを混ぜない。

次の判断に必要なのは、候補仕様の確定と小規模な比較対局である。本書を追加した時点では、公開サイト・エンジン・M1の実装状態は変えていない。

## 一次資料で確認できたこと

| 資料 | 確認したルール・知見 | この案への示唆 |
|---|---|---|
| [将棋ったー：三次元将棋](https://shogitter.com/rule/三次元将棋) | 9×9×9・372枚。玉中心の同心配置を使い、玉を詰ませると勝ち | 現行実装の準拠先。9層同一配置は別ルールになる |
| [日本中将棋連盟：中将棋のルール](https://www.chushogi-renmei.com/kouza/rule.htm) | 太子がある場合は、王だけを倒しても勝ちにならない。両方が対象になる | 複数の王相当の駒を使う将棋の先例がある |
| [将棋ったー：大局将棋](https://shogitter.com/rule/大局将棋) | 玉・太子をすべて取ると勝ち。王手放置を許し、持ち駒は使わない | 「王を取れる」「複数を倒す」方式は存在する。ただし9王・5先取・持ち駒ありの検証結果ではない |
| [Green Chess：Dual Chess](https://greenchess.net/rules.php?v=dual) | 2王とも王手から逃れる必要があり、両方を救えない同時攻撃も負けになる | 「全部の王を守る」方式も成立する。王数を増やすと守備対象が増える |
| [Lichess：Antichess](https://lichess.org/variant/antichess) | 王に通常の王としての特権がなく、王手をなくしている | 王の動きと、王手・勝敗の役割を分けて設計できる。勝敗・強制捕獲の規則は本案へ移植しない |
| [Lichess：Three-Check](https://lichess.org/variant/threeCheck) | 通常の合法手条件を保ち、3回の王手で勝てる | 回数を数える勝利条件の先例。ただし「3回王手」と「5王捕獲」は異なる |
| [Browne / Maire, Evolutionary Game Design, 2010](https://cambolbro.com/games/shibumi/Yavalath_EvolutionnaryGameDesign_c31909.pdf) | 自己対局を使って終局率・対局長・展開などを評価する。著者らも指標を普遍的な基準とはしていない | ルールの説明だけで面白さを断定せず、実測と人間による操作確認を組み合わせる根拠になる |

以上の資料は、9×9×9・各9王・5王先取が最良だと示すものではない。今回確認した範囲では、この組み合わせの比較対局データは得られていない。中将棋や大局将棋の持ち駒・特殊駒・千日手などの規則を、そのまま取り込むことも提案していない。

## 候補の比較

以下の長所・懸念は**ルール構造からの推論**であり、本プロジェクトで対局を測った結果ではない。

| 案 | 分かりやすさ・狙い | 懸念と検証事項 | 扱い |
|---|---|---|---|
| 現行：1王を詰ます | 勝利目標を1枚に集中でき、既存ルールと比較できる | 各層の配置が違う。初見で全体の構造を理解できるか確認が必要 | 研究・互換性の基準 |
| 9王・5王先取、王手なし | 各層を同じ配置にでき、5枚までの進捗を表示できる。最後の4王を追う必要がない | 王を一部犠牲にする攻め、先手有利、守備一辺倒になる可能性を測る必要がある | **最初の試作候補** |
| 9王・全9王捕獲 | 全滅という明確な終局。複数王相当をすべて倒す先例がある | 最後の王の逃走・捜索に長い手数が必要になる可能性。長期化は未実測 | 5先取との比較対象 |
| 9王・規定手数で捕獲数比較 | 「より多くの王を取った側が勝つ」という元の案に最も近い | 上限の選び方で結果が変わる。リード側が手数を消費する戦略を取れる可能性 | 手数上限の感度も比較 |
| 9王すべてに通常の王手回避を要求 | 王手・詰みの概念を維持できる | 1枚を救っても別の王が取られる同時攻撃が敗北に直結し得る。9枚分の安全確認が必要 | 最初の試作では優先しない |

「先に5枚取る」と「終了時により多く取っている」は同じ勝利条件ではない。後者を採用するには、**何をもって対局終了とするか**も決める必要がある。5先取案は、終了時点を説明しやすくするための別の提案である。

## 初期配置だけのローカル比較

エンジンコミット `caf63a0477964c269c04875082b6235572ec9922`、Rust 1.97.1のreleaseビルドで確認した。現行盤の中央V層を全9層へコピーした比較盤を作り、既存の立体移動と遮りの規則で、先手各駒の `movegen::targets` を数えた。空盤でなく、味方駒による遮りを含む。

| 項目 | 現行配置 | 9層同一配置 |
|---|---:|---:|
| 駒の総数 | 372 | 360 |
| 王の枚数（各陣営） | 1 | 9 |
| 先手の移動先候補の総数 | 424 | 554 |
| うち、出発した層と異なる層への移動先 | 214 | 284 |

ここでの候補数は**王手回避・終局・持ち駒・成りの分岐を含む新ルールの合法手数ではない**。現行初期局面の合法手424手とは別に数え、たまたま同数であることも確認した。9王の局面を、1王前提の `GameState::legal_moves` に渡して測定したものではない。

9層同一配置の候補数は、この条件では約30.7%多かった。駒が少ないことから探索が軽いとは結論できない。一方、王手回避の検査を省くと1局面の処理が軽くなる可能性もある。この値だけで対局中の分岐数・探索速度・棋力・先後の公平さ・面白さは分からない。

集計を空の出力で通さないため、駒数372/360・比較盤の各9王を明示的に検査した。各駒の移動先集合は、全729マスについて `attacks` と味方駒の占有を調べる総当たりとも照合した。同じエンジン内の別経路との一致であり、独立した新ルール全体の検証ではない。再現用コードを末尾に示す。

## 5王先取の試作仕様案（未採用）

1. 2陣営・交互に1手。9×9の通常初期配置を全9層に置き、各180枚・王9枚、合計360枚で開始する。
2. 駒の立体移動・遮り・成り・二歩・行き所のない駒の扱いは、比較のため現行を使う。同じ配置にしても、桂などの動きが通常の平面将棋になるわけではない。
3. 王手放置・王の被攻撃マスへの移動を許す。王手回避・詰み・打ち歩詰め禁止・連続王手による敗北は使わない。
4. 王も移動先で捕獲できる。捕獲した王は得点として取り除き、持ち駒にせず、再投入・復活させない。他の駒は従来どおり持ち駒にして打てる。
5. 相手の王を5枚捕獲した着手の直後に勝ち。王が他の駒へ成ることや、他の駒が王へ成ることはない。
6. 投了は投了側の負け。同一局面の4回出現と、手番側の合法手がない場合は引き分けとする。これは試作案の取り決めで、先例すべてに共通する規則ではない。
7. 比較実験には有限の手数上限を別途設ける。例として400 ply（先後各200着手）を試し、上限到達は打ち切りの引き分けとして記録する。400は採用済みの本ルールでも、適切と実測した値でもない。
8. 画面には「捕獲した王 3/5」などの進捗を表示する。従来の「王手」の強制応手表示は使わず、対象の王への攻撃を表示するなら通常の攻撃情報として区別する。

規定手数での点数比較を試す場合は、5先取・上限引き分けの仕様と混ぜず、別の評価条件として、先後の着手回数が同じになる偶数plyを使う。

## 現行実装への影響

初期配置の差し替えだけでは成立しない。以下は現行コードを読んで確認した範囲であり、変更はまだ行っていない。

| 範囲 | 必要になる検討・変更 |
|---|---|
| 盤・局面検証 | `Board::find_king` は1枚を探し、`GameState::validate` は各1王を要求する。通常駒の総数制限も現行セット向けなので、王数だけ緩めても足りない |
| 適用・合法手・終局 | 王の捕獲は `make_unchecked` の持ち駒変換が想定していない。王手回避・打ち歩詰め・連続王手・詰みの処理も、勝利条件と一緒に見直す |
| 棋譜・ハッシュ・再現性 | ルールID・終局理由・得点を追跡する。異なるルールの局面を探索の置換表で混同しない。既存のZobrist固定値は変更しない |
| AI・データ・モデル | 王の安全・詰み中心の評価から、捕獲数と先取勝利に対応した評価へ変わる。M1の戦術テストと、後続の教師ラベル・終局ラベルもルールごとに用意する |
| Web | 勝敗理由・得点・攻撃表示・棋譜入出力を対応させる。対局モードは引き続き人間対AI・AI観戦で、人間同士やマルチプレイは追加しない |

## 採否を判断する次の検証案（未実施）

**目的**: 5先取が、9王全滅・規定手数の得点比較に比べて、分かりやすく適度な長さで終わり、立体移動を活用できるか調べる。現行1王も基準として測る。

**ゴール**: 各候補の仕様を固定し、下記の実測と人間対AIでの操作確認を基に採否を記録できること。候補ごとに別のゲームなので、異なるルール同士を直接対戦させて勝率を比べない。

- まず少数の固定seedで、勝敗境界・王を持ち駒にしないこと・繰り返し・undo/redo・棋譜再生を検査する。期待値は手作り局面で用意する。
- 9王の候補間では初期配置・駒の移動・持ち駒を固定し、勝利条件を変えて比較する。現行1王との比較には配置の違いも含まれるので、差を王の枚数や勝利条件だけの効果とは断定しない。
- ランダムAIと捕獲優先AIで進行の異常を探し、その後、各候補内で同じ条件の探索AIを使う。ランダム対局だけでバランスや面白さを判定しない。
- 初回の比較規模案は候補ごとに100 seed×先後交換の2局＝200局。CPU時間を小規模実行で見てから実行規模を決める。学習やGPUレンタルは不要。
- 終局率、打ち切り・繰り返し率、対局長の中央値と上位側の長さ、先手勝率と引き分け率、最初の王捕獲までの手数、層をまたぐ着手率、探索時間・ノード数を記録する。seedの組と先後交換を保った不確実性の評価も付ける。
- 手数上限や探索量を変えて結論が変わるかを確認する。説明の理解しやすさ、対象の王を見失わないか、リード後も攻防が続くかは、人間対AIの実機操作でも確認する。
- 最終判断は、これらの実測と操作結果で行う。現時点の「5先取を最初に試す」という提案を、採用決定や優位性の実証とは扱わない。

## 初期配置比較の再現コード

製品ルールを変更しない一時プログラム。リポジトリ内で `cargo build --offline --locked --release -p voxelshogi-core` を実行した後、下記を一時ファイルに保存して同じRust版でcoreへリンクする。`movegen::targets` の定義は [movegen.rs](../crates/voxelshogi-core/src/movegen.rs)、配置の定義は [board.rs](../crates/voxelshogi-core/src/board.rs) を参照。

```rust
use voxelshogi_core::{Board, Color, GameState, PieceKind, Square, movegen};

fn measure(label: &str, board: &Board) {
    let mut moves = [0usize; 14];
    let mut cross = 0usize;
    let mut kings = [0usize; 2];
    for (from, piece) in board.pieces() {
        if piece.kind == PieceKind::King { kings[piece.color.index()] += 1; }
        if piece.color != Color::Black { continue; }
        let mut destinations = movegen::targets(board, from);
        destinations.sort();
        let mut reference: Vec<_> = Square::all()
            .filter(|&to| board.get(to).is_none_or(|p| p.color != piece.color)
                && movegen::attacks(board, from, to)).collect();
        reference.sort();
        assert_eq!(destinations, reference, "target generation disagrees for {from}");
        moves[piece.kind as usize] += destinations.len();
        cross += destinations.iter().filter(|to| to.z() != from.z()).count();
    }
    println!("{label}: pieces={}, kings={kings:?}, pseudo_destinations={}, cross_layer={cross}",
        board.count(), moves.iter().sum::<usize>());
    for kind in PieceKind::ALL {
        if moves[kind as usize] > 0 { println!("  {kind:?}: {}", moves[kind as usize]); }
    }
}
fn main() {
    let standard = Board::initial();
    let mut repeated = Board::empty();
    for z in 0..9 {
        for y in 0..9 {
            for x in 0..9 {
                repeated.set(Square::new(x, y, z), standard.get(Square::new(x, y, 4)));
            }
        }
    }
    assert_eq!(standard.count(), 372);
    assert_eq!(repeated.count(), 360);
    for side in Color::ALL {
        assert_eq!(repeated.pieces().filter(|(_, p)| p.color == side && p.kind == PieceKind::King).count(), 9);
    }
    println!("standard legal_moves={}", GameState::new().legal_moves().len());
    measure("current", &standard);
    measure("nine_identical_layers", &repeated);
}
```

上記プログラムのSHA-256: `4204e8ce775f4e4bb2c4213f326e21493bdf95c03ce9c66ea0724fbf2f379af7`。リンク時はworkspaceのreleaseと同じthin LTOを使い、例として `rustc --edition=2024 -O -C lto=thin -C codegen-units=1 -L dependency=target/release/deps --extern voxelshogi_core=target/release/deps/<そのビルドのlibvoxelshogi_core-….rlib> <一時ファイル.rs> -o <一時実行ファイル>` で実行できる。
