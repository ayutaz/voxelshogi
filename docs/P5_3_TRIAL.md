# P5-3：8局の実GPU時間試行

2026-11-04 JST。ユーザーの「5まで進めて」の最初の有料単位。[全体の実行順](P5_3_PLAN.md)のP5-3bに対応する。評価基盤の検証後に起動し、結果・時間・保存・資源終了を確認して150局の見積もりへ進む。まだ実行結果ではない。

## 目的と数量ゴール

- M6基点とP5-2最後の子モデルを、時間試行専用の2開始局面で先後交換する。2モデル×2局面×2色＝8局。15開始局面の本比較とは別集合にし、8局を150局へ合算しない。
- 固定HF revisionの重み・全P5-2 dataset/state・M4コーパス・保護集合をLinuxで取得し、bytes／hashを照合する。復旧・子モデル再exportのhashも確認する。
- source・モデルhash・case・seed・探索／追加手数上限を実対局前に固定する。同じTorch CUDA FP32合法argmax対、深さ3／20,000ノード／TT4,096のM1を用いる。
- 8／8局のRust全手再生・再集計と、開始後の全局面／終端について物理局面と正規化入力の監査を行う。空のコーパスを合格とせず、重複があれば実数・出所を保存する。
- 完全／部分・失敗を区別したDataset Cardと実棋譜・集計・条件をHFへ保存し、public/manual・Community OFFと固定revisionの全ファイルhashを確認する。データはMacへ中継しない。
- 使用した課金実機・volumeが0になったことを確認する。完走できなかった場合も、既存PID・終了状態・保存receiptを調べてから継続方針を決め、観測時間切れだけで重複起動しない。

## 最初の見積もりと配分

読み取り事前確認では、RTX5090×1・80GBのディスクを含む候補単価が約US$0.98049/時だった。これは在庫保証ではなく、起動直前に再取得・適合確認する。1／2／4GPU候補の在庫は確認できたが、この試行で借りるのは単GPUだけである。

試行の上限は2時間・US$2。computeの計画値は75分、実際の停止は絶対期限と退避・終了の余裕を含む制御で行う。1時間当たりUS$1以下・転送無料・80GBを含む既存の狭いquote契約を維持し、価格・資源・guardの条件が合わなければ借りない。準備・取得・復旧・全コーパス監査・HF転送／照合もこの2時間に含む。この見積もりは完了時間の保証ではなく、150局の費用は8局の実測後に決める。

既存の全体予約はUS$85／100、Phase5予約24／配分24、Phase6配分15。未使用Phase6からUS$2だけをPhase5へ移し、配分を26・13、合計39とする変更を準備する。予約済み85を減らさず、基本総枠100と条件付き追加100未適用も維持する。試行を予約した時点では全体予約87、Phase5予約26となる予定で、配分変更自体は課金や予約ではない。

controllerの配分と共通ledgerの`research_allocations_usd`の完全一致を新規課金要求前に検査する。コードの統合・関連CI後に、過去の全予約を保持したままledgerの配分と根拠を更新する。コードだけ26・13でledgerが24・15のままの場合や、配分の欠落・増額を拒否する。

## 実行・保存・次への判断

GitHub Actionsの独立期限guardと制御側の予備終了監視、専用label・所有ID・workload hash・SSH鍵を使う。providerキーは制御側、必要なHF認証は承認済みのSSH標準入力と一時環境／メモリだけに置く。再利用できるコード・条件・公開ハーネスの準備とLinux検証を先に済ませ、GPUを実装待ちにしない。

準備・取得、復旧、局面生成、各モデルの対局、Rust再生、コーパス監査、HF保存／照合、終了を別々に測る。CPU／GPU利用・VRAM・RSSも出所と対象範囲を示す。8局の勝敗は時間試行の観測であり、一般的な棋力や150局の区間精度を主張しない。

成功後は実測と当時の見積もりを併記して本比較の実行枠を決める。必要な単位ごとに配分・累積予約を確認し、基本枠不足が実測見積もりで判明した場合だけ承認済みの条件付き追加枠を適用する。8局の結果を見て本比較の15局面を選び直さず、条件変更が必要なら新protocolへ分ける。
