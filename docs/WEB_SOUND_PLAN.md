# Web版の効果音：調査と実装計画

2026-11-15 JST。対象はAI観戦と人間対AI。目的は、画面を見続けなくても着手・捕獲・局面の節目に気付き、盤の動きを追いやすくすること。ユーザーの「4まで」に基づき、試作・実装・公開ブラウザ確認を実施した。物理スピーカーの聴感と実スマホは未確認として残す。[実装と証拠の現在地](WEB_SOUND_VALIDATION.md)。動画BGMの制作は[別の記録](DEMO_BGM.md)で扱う。

## 調査で分かったこと

- 調査開始時点では`apps/web/src`に音声再生実装はなかった。人間は`App.tsx`の`play()`、AIは`ArenaController`から`GameStore.applyAiMove()`→`GameStore.play()`へ入る。成功した着手をこの共通点で観測すれば、2D／3D・AI難易度ごとの実装は不要。
- `GameStore.changed()`は着手だけでなく`goto()`・新規対局・読み込み・投了にも使う。`revision`や`lastMove`の変化をそのまま音へ結ぶと、履歴移動・置換・React再描画で誤音や重複が起きる。
- `Snapshot`の着手前の`board`と`parseMove(move).to`から捕獲を識別できる。`inCheck`・`result`で王手と終局も取得でき、将棋ルールをJSで再実装する必要はない。
- ブラウザは音声の自動再生を制限する。ユーザーが押す開始ボタンや音ボタンのイベント内で`AudioContext`を作成／resumeする。[Chrome公式](https://developer.chrome.com/blog/web-audio-autoplay)・[MDN autoplay](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)。
- 短いSEには、一度decodeした`AudioBuffer`を再利用し、再生ごとに`AudioBufferSourceNode`を作る方法が合う。Contextはアプリで1個とする。[MDN best practices](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)・[AudioBufferSourceNode](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode)。
- 音量・ミュートを設け、音だけで必要な情報を伝えない。[Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/provide-separate-volume-controls-or-mutes-for-effects-speech-and-background-music/)。iOSの割り込み後の復帰は実機確認が必要で、Linux Chromiumの成功で代用しない。[MDN context state](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/state)。

## どこに、どの音を付けるか

基本は短い木質音。音の数を絞り、毎回聞く移動音は控えめにする。下表の長さ・音量は実装時の初期目標であり、聴感確認後に調整する。

| 場面 | 音の案 | 発火する条件・場所 | 優先度 |
|---|---|---|---|
| 通常移動・駒打ち | 60〜100msの乾いた「コツ」 | `GameStore.play()`が成功し、着手先が空だった時。人間・AI・異層移動で共通 | 最初に実装 |
| 駒を取る／取られる | 100〜160msの少し低く重い「カッ」 | 受理済み着手の、着手前の移動先に相手駒があった時。通常移動音と二重に鳴らさない | 最初に実装 |
| 人間側の駒が取られた | 捕獲音の低い変種 | 人間対AIの時だけ、人間側の駒の捕獲に適用。音量を大きくせず区別する。AI観戦は中立の捕獲音 | 捕獲の基本確認後 |
| 成り | 木質音に短い明るい余韻、全体120〜180ms | 成りの選択ダイアログでは鳴らさず、成る着手の成功後 | 第2段階 |
| 王手 | 短く控えめな2音、180〜250ms | 成功した着手後、次の手番側が王手になった時に1回。思考中や再描画では繰り返さない | 第2段階 |
| 終局・投了 | 観戦は中立の短い終止音、人間対AIは穏やかな勝敗音、300〜500ms | ライブ対局が未終局→終局へ移った時。読み込んだ終局棋譜には鳴らさない | 第2段階 |

同時成立は**終局 > 王手 > 捕獲 > 成り > 通常移動／駒打ち**の1主音にまとめる。王を取る専用音や9王ルールの演出は追加しない。3Dカメラの位置で音を振り分けず、最初は中央から聞こえる音でそろえる。

選択・hover・カメラ回転・層の切替・AI思考中・モデル読み込み完了・通信の自動再送にはSEを付けない。指せないマスや選択取消にも警告音を連打しない。

## 操作と鳴らさない条件

- 初期設定はSE ON・控えめな音量（初期案35%）。ページを開いただけでは鳴らさず、「観戦を開始」「対戦をはじめる」「音をON」の直接操作で準備する。
- 上部ヘッダーに44×44px以上のミュートボタンを置き、読み上げ用の名前と状態を付ける。音量とテスト音は既存の「表示設定」シート内のサウンド欄へ置く。390pxでも対局操作を押し出さないことを画像・寸法で確認する。
- ON/OFF・音量だけをlocalStorageへ保存。保存禁止環境でも現在のページで操作できるよう例外を処理する。HF・Cloudflareへの音声設定送信は不要。
- ミュート時は再生中の音も短く減衰して止める。非表示タブではSEを抑止し、復帰時に過去の音をまとめて再生しない。非表示中にAI対局をどう進めるかは既存の対局制御を維持する。
- 「1手進む」は、表示中の局面から次の1手へ進めた時だけ短い移動／捕獲音を鳴らしてよい。戻る・任意手数へのジャンプ・読み込み・リセット・対局設定変更では鳴らさない。自動再生を追加する場合も同じ規則を使う。
- 高速観戦では移動系SEの間隔を最低120ms、同時発音は最大2音に制限し、古い音の予約は破棄する。イベントは保存するが、音を全手分並べて後から遅れて鳴らさない。終局は最後に1回。
- 駒・王手表示・直前手・終局表示は音がなくても使える。再生拒否・decode失敗・Context復帰失敗が対局や保存を止めることはない。

## 実装の分け方

`game/store.ts`へ、受理した操作の意味だけを通知する小さい表示イベントを追加する。イベントIDは対局ID＋連番、種別はライブ着手・明示1手送り・終局等を区別する。合法性はWASMが判定した結果を使う。音声コード・ブラウザAPI・素材はstoreへ入れない。

新しい`audio/`の純粋な分類処理で、イベントと着手前後の状態から音種を1つ選ぶ。再生を担当するモジュールはdedupe・音量・音数制限・Context解放を管理する。React StrictModeのeffect再実行やAppの再描画で二重登録しない。`applyAiMove()`の古い応答拒否、モデル失敗、中断時には着手イベントが発生しないことを確認する。

素材はまず自作の短い合成音で木質のmove／captureを2種類ずつ試作し、最終的に各1種類へ絞る。外部SEの候補には[Kenney Interface Sounds](https://kenney.nl/assets/interface-sounds)（公式表示CC0）があるが、未試聴で採用済みとはしない。採用時は配布元・個別license・加工・hashを記録し、音源は同一originで配信する。新しい音声SDKやCDNを最初から増やさない。

共通の受理イベントと音種の優先判定を一度に検査できる小さい実装になったため、S1〜S3を1つのPRへまとめ、S4の候補・公開検証を同じ変更に結び付ける。各PRは作業ブランチ・TDD・既知バグ注入・適した軽量ローカル確認・Linux結合検証・必須8件成功後の通常mergeで進める。音のためにGPU・学習・ルール変更は不要。

## 検証する具体例

単体は少なくとも次の12ケースを独立した小さい局面・イベントで作る：通常移動、駒打ち、捕獲、人間側捕獲、成り、王手＋捕獲の優先、終局＋王手の優先、stale AI拒否、不正着手、同一IDの重複、履歴ジャンプ、初期化／読み込み。別にミュート・非表示・高速120ms制限・保存拒否・Context失敗の境界を検査する。分類の期待値はテスト側で手書きし、本実装を正解生成に使わない。

E2EはLinuxで実AudioContextを使用し、開始前の無音、開始操作後の通常着手、捕獲、ミュート、履歴／非表示からの復帰、失敗時も対局継続の6経路を検証する。Buffer再生の呼び出しだけで「聞こえた」と扱わず、実経路に接続したAnalyser等の非ゼロ信号も確認する。端末のスピーカー出力・聴感・Bluetooth遅延の実機証明とは分ける。既存の53 UI E2E・人間／AI対局・カメラ・モデル・自動保存が壊れていないことも変更範囲に応じて確認する。

Macは編集・軽量な純粋テスト・短い完成素材の試聴に使う。合成・音量解析・録画・エンコードと重い回帰はLinuxで行う。CIで測った時刻をMac／実スマホの音声遅延の測定値へ流用しない。

## 実装時の具体化

今回のSEは短い自作の木質共鳴音をPCMとして生成し、AudioBufferへ保存する。ブラウザへ外部音源を取りに行かず、同一originの検証済みJSに生成処理を含める。初回は各音が必要になった時だけPCMを作り、その後は再利用する。したがって外部音源のfetch／decode段階はなく、Context・buffer生成・再生の失敗で対局が止まらないことを検証する。Linuxで同じ処理から試聴用WAV（移動・捕獲各2案＋採用8音）を作り、100KiB目標は採用8音のPCM16 WAV合計でも検査する。

## 実施結果

#199を通常mergeし、公開source `ba9767a`でChromium／WebKitのSE全22件、既存UI全53件、カメラ3回、モデル6件が成功した。採用8音の試聴WAV合計は84,144 bytes。Safari 27.0.1でも設定変更・保持・試聴操作を確認した。S1は音の試作と設計上の選定までで、物理スピーカーでの聴感評価を済み扱いしない。[測定・失敗履歴・未確認範囲](WEB_SOUND_VALIDATION.md)と[固定記録](experiments/web-sound-public-20261115.md)を参照する。
