## (3) 推奨する情報設計：「盤ステージ＋9層レール＋一文実況」

**各要素の役割**
- **2D「着手層」盤（主役）**：何が起きたかを読む場所。直前手の層を自動で追い、手動で層を変えたら「最新手へ戻る」チップを出します。
- **9層レール（常に表示）**：どこで起きたかを示す場所です。
  - I〜IXの小さな盤を並べ、駒の有無、移動元の層（輪郭線）、移動先の層（塗り）、玉、王手（赤）を表示します。
  - タップするとその層を2Dで表示します。
  - 人間対AIの手番では、既存の `layerTargets`（spectator.ts:12）で層ごとの移動先の数を表示します。
- **3D（フック兼、空間の補助）**：同じ色で強調し、層番号ラベルと軌跡を表示します。
- **一文実況**：例「☖後手 歩 9三→9四（IX層内）」。層をまたぐ手では「VII層→IX層」を強調します。

**PC（1440×900）**
- 上部の細いバー：ロゴ、対戦カード、手数と手番、「研究ツール」「?」。
- 左55%：3Dステージ（層ラベル付き、視点リセットあり）。
- 右45%：2D着手層盤（マス56px以上）、その上に一文実況、下に横向きの9層レール。
- 画面下の固定バー：▶/⏸、1手、速度（ゆっくり／普通／速い）、手数スライダー（履歴）。
- 右からの引き出し：対局、表示、棋譜、モデル、データ送信、研究ログ。

**モバイル（390×844）**
- 上から順に：対戦カード（40px）、横向き9層レール（48px、右端に3Dの縮小表示があり、タップで全画面3D）、一文実況、2D盤（横幅いっぱい、マス約38px）。
- 下部の固定バー（64px）と、設定のボトムシート。

**状態ごとの見え方**

| 状態 | 表示 |
|---|---|
| 初期 | 対戦カード（既定は☗Normal vs ☖Normal）、大きな「▶ 観戦を開始」、説明1行、「送信：OFF」チップ、初期局面の9層レール |
| 観戦中 | 実況を毎手更新、「☗Normal 思考中…」の表示、移動先の層がレール上で軽く点滅、移動元はゴースト表示 |
| 停止中／履歴 | 「履歴 23/41手 — 最新へ」の帯。1手指すと分岐することを、ここで明示 |
| 終局 | 盤の上に終局カード（`resultText`、手数）。送信に同意していれば送信状態も表示 |
| 設定 | 引き出しのタブ：対局（モード、各席のAI、思考上限）、表示（軌跡、層の濃さ、段・筋の断面は詳細へ）、棋譜（保存、AI条件付き保存、読み込み、手順リスト）、送信、モデル |
| モデル失敗 | 席チップを赤にし、失敗カード（`guidance()` の文、再試行、Normalで新しい対局、技術情報）を出す |

**モデル失敗時の注意**：席のAIを途中で切り替えると、記録が実際の対局条件とずれるおそれがあります。保存時のAI条件は、その時点の設定から作られているためです（App.tsx:157, GameCollectionPanel.tsx:41 `selected-at-submission`）。そのため「新しい対局として開始」を基本にすることを勧めます。

**研究モデル比較向け**：対戦カードに各席の条件（モデルID、精度、実行先、SHAの先頭）を並べ、研究ログに毎手のValue（モデル出力、直前AIの視点と明記）と推論msを表にします。勝率への換算や新しい指標は作りません。

## (5) モックの合格条件（測れる形）

1. **最初の画面（スクロールなし）に収まること**：1440×900と390×844で、9×9の81マス、9層レール、主ボタンがすべて入る。スクリーンショットの要素の座標で判定します。
2. **マスの大きさ**：390幅で36px以上、1440幅で56px以上。
3. **観戦開始までの操作**：読み込み後1タップ。終局からの「もう一局」も1タップ（未保存の確認ダイアログは除く）。
4. **層をまたぐ手**：対象の手すべてで、レールの移動元と移動先、2Dのゴースト、実況の「X層→Y層」がそろう。
5. **直前手の強調**：空きマスとのコントラスト比が3:1以上（WCAGの非テキスト基準）。
6. **既定表示の文言**：通常の画面に「ノード」「往復」「停止理由」が出ない。同時に、現在の計測項目（App.tsx:355-364）がすべて研究ログで見られる（対応表で確認）。
7. **機能を減らさない**：現行の全操作（モード、投了、戻る・進む、各席のAI、モデルの条件、思考上限、待ち時間、保存・AI条件付き保存・読み込み、手順リスト、表示、軌跡、層の濃さ、段・筋の断面、送信と中断送信、成り選択）が、引き出しから2タップ以内に届く。
8. **送信のルール**：対局ごとに既定OFF、初手より前にONにできる、観戦中は状態チップが常に見える、終局後はONにできない。現行の条件と完全に同じであること。
9. **モデル失敗時**：説明と2つ以上の次の操作を出し、自動でNormalへ切り替えない。
10. **モバイルの観戦中**：ページのスクロール量がゼロ。3Dの縮小表示の上でもページのスクロールが妨げられない。
11. **未実証の指標を出さない**：推定勝率や改善率などの表示がゼロ件。

## (6) 未確認事項と、実ユーザーで確かめる仮説

**未確認事項**
- 実機（実際のスマホ、Safari、iOSのフォルダー選択、WebGPU）での動作と3Dの性能。今回は実機操作をしていません。
- 画像では1100px以下でも設定が開いていますが、コードでは初期は閉じます（App.tsx:52）。撮影時の手順が分かりません。
- 画像はEasy vs Easyですが、コードの既定はNormal同士です（App.tsx:37）。撮影時に設定を変えたものと推測しています。
- 初期配置で各層に駒がどう並ぶかは、今回読んだ範囲では確認できていません。
- Easy/Normalで1局が何手で終わるか、層をまたぐ手の頻度。観戦を続けられる長さかどうかに直結します。
- モデルSの読み込み時間、本番環境での `/api/collection` の挙動。

**実ユーザーで確かめる仮説**（5〜8人程度の観察テストを想定。閲覧の追跡機能は同意の範囲外なので追加しない前提です）
- H1：最初の画面で3Dか9層レールが見えると、「何の将棋か」を数秒以内に説明できる人が増える。
- H2：9層レールと移動元のゴーストがあれば、層をまたぐ手を正しく言える。
- H3：自動開始とボタンでの開始のどちらが、離脱が少なく好まれるか。
- H4：一文実況だけで観戦を続けたいと感じ、研究者は引き出しの研究ログで足りる。
- H5：既定の速度（待ち時間400ms）は初見には速すぎる。
- H6：モバイルの観戦者は設定をほとんど開かない。
