# Architecture Decision Records

各ADRは当時の「状況 → 決定 → 理由 → 影響」を記録する。後続ADRと現行設定を優先し、旧件数・未実装の影響を現在の実績と混同しない。現在はADR-017のM1まで実装・検証し、標準1王のライブ画面と9王の固定棋譜比較室を併存させている。M2のライブ探索・モデル推論は未実装（[進捗](ROADMAP.md)）。新しい決定は末尾に追記する。

## ADR-001: ルールは Rust の単一エンジンに集約する（2026-10-25）

- **状況**: Web・Python（データ生成・学習）・探索のそれぞれでルールを実装すると、実装間でずれが生じ、そのずれが学習データを汚す。
- **決定**: `voxelshogi-core`（依存は serde と serde_json のみ）にルールを実装する。WASM（wasm-bindgen）と Python（PyO3、予定）は薄いラッパーにする。Web の TypeScript は、エンジンの出力（駒コード・指し手文字列）をデコードするだけにする。
- **影響**: UI の合法手ハイライトも、エンジンが返す合法手リストから作る。TS 側に利きの計算はない。

## ADR-002: ルール準拠先は将棋ったー三次元将棋（10/17 改定後）（2026-10-25）

- **決定**: `ruleset_id = voxelshogi-standard-v1` を、将棋ったー rule 166 の 2026-10-17 改定版とする（ユーザー承認済み）。詳細と独自に判断した部分は `docs/RULESET.md` に記載する。
- **理由**: 既存のプレイヤーと棋譜があり、ルールが一次資料として最も具体的だから。tomikan/3D_shogi は駒の動きが大きく異なり、ライセンスもない（`docs/RELATED_WORK.md`）。

## ADR-003: 検証は「独立した参照実装との一致」を軸にする（2026-10-25）

- **状況**: 三次元将棋には、既知の perft 値がない。エンジンの出力を正解値にすると、誤りが固定されてしまう。
- **決定**: テスト側に、ルール文を素朴に書き写した参照実装を置く。対象は利き・合法手・打ち歩詰めで、本実装のような動的計画法は使わない。ランダム盤面・ランダム局面・ランダム対局の全手で、本実装と一致することを確認する。手計算できる値（空盤での利きの数、遮りの領域など）は、個別のテストにする。さらに、変異テストでテストの検出力を確認する。
- **影響**: 参照実装は遅いため、テストのプロファイルは opt-level 2 にしている。

## ADR-004: 飛車・角の利きは動的計画法で生成する（2026-10-25）

- **決定**: 飛車は、象限ごとに「長方形が空か」を漸化式 `F(u,v)` で求める。角は、平面と立ち上がり方向の組ごとに、台形の列が空かを漸化式で求める。空間対角は、3つの台形の判定がすべて空いている場合に許可する。
- **理由**: すべての遮り駒を総当たりすると O(移動先×駒数) になる。動的計画法なら O(81) 程度で済む。
- **注意**: 角の台形は始点に依存し、非対称である。そのため、王手の判定（`attacks`）は攻撃側の駒から順方向に評価する。

## ADR-005: 局面の文字列表記は独自の VSFEN（2026-10-25）

- **決定**: SFEN を拡張し、層は `|`、段は `/` で区切る。筋は9→1の順に並べる。持ち駒と手数の書き方は SFEN と同じ。詳細は `crates/voxelshogi-core/src/notation.rs` に記載。
- **理由**: 人間が読める形にしたい。SFEN と似せておけば、既存のツールの知識を流用できる。

## ADR-006: Web は Vite + React + three/R3F。3D と 2D 断面を併用する（2026-10-25）

- **決定**: 3D 表示は全体を把握するためのもので、注目層を強調し、他の層を半透明にする。正確な操作は 2D 断面（層・段・筋の3方向）で行う。駒は (駒種×色) ごとに InstancedMesh で描画する。
- **理由**: 372枚の駒を同時に表示すると、奥の駒が重なって指し手を正確に選べない。描画負荷を抑えるため、ドローコールを抑える。30回程度は初期目標で、現在の実測値ではない。

## ADR-007: WASM は wasm-bindgen-cli を直接使う（2026-10-25）

- **決定**: wasm-pack は使わない。`cargo build --target wasm32-unknown-unknown` の後に、`wasm-bindgen --target web` を実行する（`scripts/build-wasm.sh`）。wasm-bindgen のバージョンは Cargo と CLI で `=0.2.129` に固定する。
- **理由**: ツールを減らし、CI でのインストールを `taiki-e/install-action` で速くするため。wasm-opt による最適化は、後で必要になってから追加する。

## ADR-008: デプロイは GitHub Actions から行う（Cloudflare Git 連携は使わない）（2026-10-25）

- **決定**: CI で Rust・Web 単体・E2E のテストが通った後、同じワークフローで `wrangler deploy` を実行する。初期は Secrets 未登録時にスキップしたが、M0-4 で本番の設定漏れは失敗に変更済み。PR・通常の手動 CI は本番公開しない。
- **状態**: 2026-10-25 に Secrets を登録し、main への push で自動デプロイされることを確認した。
- **理由**:
  - Rust と wasm-bindgen のツールチェーン管理とキャッシュを、1か所にまとめられる。
  - テストに失敗した状態ではデプロイされないことを保証できる。
  - ビルドを二重に行わずに済む。
- **トレードオフ**: Git 連携が提供する PR プレビュー URL は、使わない。必要になれば `wrangler versions upload` で代替する。

## ADR-009: Static Assets のみで配信する（Worker スクリプトなし）（2026-10-25）

- **決定**: `wrangler.jsonc` には `assets` だけを設定し、`not_found_handling: single-page-application` にする。
- **理由**: 静的アセットへのリクエストは Worker を起動しないため、無料かつ回数無制限である（`docs/COST_ESTIMATE.md` §5）。
- **影響**: 25MiB を超えるファイル（ONNX Runtime の WebGPU 用 wasm、大きなモデル）は、Static Assetsに同居できない。M3で軽量ビルドやR2等の配信を選定する（未決定）。

## ADR-010: Cloudflare はプロジェクト専用のログインで操作する（2026-10-25）

- **状況**: このマシンの wrangler はグローバルには別のアカウントでログインしており、Chrome もさらに別のアカウントでログインしている。そのままコマンドを実行すると、本プロジェクトが別のアカウントにデプロイされる恐れがある。
- **決定**: デプロイ先は、ユーザーの個人アカウントとする（ユーザー指定）。ローカルの wrangler は、必ず `scripts/cf.sh` から起動する。このスクリプトは、`XDG_CONFIG_HOME` を `.cloudflare-cli/`（gitignore 済み）に向けて、ログイン情報をプロジェクト内に閉じ込める。`apps/web` の `pnpm run deploy` も、このスクリプトを経由する。
- **理由**: グローバルのログインを変えずに済み、他のプロジェクトに影響しない。誤ったアカウントへのデプロイを、仕組みで防げる。
- **影響**: CI 用の API トークンは、CLI の OAuth ログインでは作れないため、ダッシュボードで作る（`docs/DEPLOYMENT.md`）。公開サイトの検証は、`E2E_BASE_URL` を指定して E2E テストを公開 URL に対して実行する。

## ADR-011: 本番の版とテスト済みコミットを照合する（2026-10-25）

- **状況**: HTML の文字列確認だけでは JS/WASM の配信不良を検出できず、CI が検証した版と公開 URL の版も照合できなかった。全 workflow の中断設定により deploy が途中で中断される可能性もあった。
- **決定**: `web-dist` に commit SHA を付け、同じ run の成果物を公開する。production の deploy と公開検証を直列化し、ロック取得後に古い候補を除外する。配信 SHA と実ブラウザ E2E の両方が成功した版の Cloudflare version ID を保存する。
- **理由**: PR のテスト、統合後のテスト、実際の配信の成功をそれぞれ検証でき、復旧先も具体的に選べる。
- **影響**: Cloudflare 認証は production environment に閉じる。設定漏れは失敗とし、公開後の一時的な E2E 失敗だけで自動 rollback は行わない。復旧手順は `docs/DEPLOYMENT.md` に記録し、隔離した artifact の再配信で検証する。初回の本番検証と移行は M0-4 の記録で追跡する。

## ADR-012: 対局モードを人間対AIとAI観戦に限定する（2026-10-25）

- **状況**: ユーザーから、人間同士の対局・マルチプレイは実装対象に含めないと明示された。
- **決定**: 対局モードは人間（先手）vs AI、人間（後手）vs AI、AI vs AI 観戦の3種類とする。初期表示は人間が先手のAI対局とし、棋譜の読み込みでも人間同士のモードへ切り替えない。
- **理由**: 指定されたプロジェクトのスコープを、画面・テスト・開発計画で一致させる。
- **影響**: ローカル・オンライン双方の人間同士の対局とマルチプレイを後続フェーズにも追加しない。人間の先手・後手のAI対局、観戦、棋譜の入出力を E2E で検証する。

## ADR-013: 変更前のブランチ作成と PR の必須チェックを要求する（2026-10-25）

- **状況**: main の直接 push を許していた。ユーザーから main 保護、実装時のブランチ作成、関連 CI の PR 実行を要求された。
- **決定**: 変更前に作業ブランチを作り、PR 経由で取り込む。main の ruleset は最新 main に対する7チェックと CodeQL の error / high以上の検出を要求し、force push・削除と管理者を含む bypass を禁止する。他者承認の必須数は0とする。
- **理由**: 一人開発を続けながら、テスト・監査・解析を通らない変更の取り込みを防ぐ。
- **影響**: PR では通常 CI、CodeQL、Rust/Web カバレッジ、既知変異を実行する（当初9件、ADR-016のR0後は14件）。全体変異調査は週次・手動とし、本番 deploy は main への統合後だけで行う。`AGENTS.md`・`CONTRIBUTING.md`・PR テンプレートと `.github/main-ruleset.json` に運用・設定を保存する。

## ADR-014: 配信用の変換済みモデルをそのまま実機デモで試せるようにする（2026-10-25）

- **状況**: ユーザーから、実機で動く変換済みモデルの Web デモと、量子化などで精度が変わる版もそのまま試せることを要求された。
- **決定**: Web 向けに作成・評価した実行可能な各変換版を、採用版・比較版とも実機のブラウザで選択・実行できるようにする。精度が下がった版も対象とする。評価対象と配信ファイルの SHA-256 を一致させ、モデル ID、精度形式、backend、変換設定を追跡する。変換前との精度・棋力・速度・サイズの差を記録する。
- **理由**: ユーザーが触れるモデルと、評価・報告したモデルを一致させ、軽量化の効果と精度への影響を実際に比較できるようにする。
- **影響**: M3 で精度形式別の対応確認と実機技術デモ、M6 で学習済みの各変換版の評価と対局・観戦 UI を実装する。runtime 間の数値比較と量子化による差は分けて検証し、未対応 backend は明示する。モデル選択は Phase 7 まで先送りしない。

## ADR-015: AI対AIの観戦を主用途とし、そのためのモデル開発・研究を行う（2026-10-26）

- **状況**: ユーザーから、ゲームとして面白く、分かりやすく、見映えのよいAI対AIを見て・眺めることが主目的で、そのためのモデル開発と研究を行うと明示された。人間が参加する場合は人間対AIだけを想定する。
- **決定**: AI vs AI観戦を主用途、人間 vs AIを補助機能とする。観戦の自動進行、停止・1手送り・速度変更、盤面と重要イベントの可読性、両AIのモデルと条件の識別を優先する。人間同士の対局・マルチプレイは引き続き対象外とする。
- **理由**: ルールの採否、モデル評価、画面の優先順位を、ユーザーが求める観戦と研究の体験にそろえる。棋力・ルールの性質と、再生速度・カメラなどの表示をそれぞれ検証する。
- **影響**: 初期導線は観戦を中心にする方針をADR-012の初期表示方針より優先し、画面の変更はM2以降で実施する。M2で探索AI同士の観戦、M3で3D表示と推論の同時動作、M6で各モデル・変換版を両AIに選んだ観戦と比較を検証する。9王・5先取は調査中の候補であり、本ADRは採用を決めるものではない。

## ADR-016: ルール比較用の9王エンジンと固定棋譜再生を分ける（2026-10-26）

- **状況**: ユーザーが全王捕獲・規定手数採点も含むAI比較と、同じ棋譜での観戦表示試作を要求した。現行エンジンは1王・王手回避を前提としている。
- **決定**: 9王の実験はcoreの別モジュール `capture`、幅制限探索と実験棋譜は `experiment`、WASMは薄い `ExperimentReplay` とする。3候補に別IDを与え、標準の局面・棋譜APIを維持する。WebはCPU生成済みの実対局をRustで全手検証して再生し、表示A/Bの変更は確定した着手列に影響させない。
- **理由**: 多王の安全判定を1王用処理へ紛れ込ませず、候補ルールの成績と表示の効果を分けて検証する。棋譜のSHA-256と局面ハッシュで、測定・表示した対象を追跡する。
- **影響**: R0は正式採用・M1完成・ブラウザ内ライブ探索・学習モデル推論の完成を意味しない。実装版を固定した対照と手数／探索幅の感度を記録し、M1の強い探索と観戦者の理解度評価で採否を再検討する。必須の既知変異回帰は9件から14件へ拡充した。


## ADR-017: 標準1王のM1探索と履歴を区別する置換表（2026-10-26）

- **状況**: R0の幅制限探索では全合法手のminimax値を保証できない。WebのNormalと教師生成には、全幅探索・固定条件での再現性・深さ／ノード／時間上限が必要。
- **決定**: `search` モジュールに標準1王のαβを実装。評価は手番側の駒得と±1,000,000の終局値、詰み距離補正なし。反復深化・手の並べ替え・置換表を個別に切り替え、未完了反復は採用しない。WASMの時計を注入できるAPIを用意する。
- **理由**: 候補の省略を行わず、独立した全探索と照合できる。置換表は呼び出し単位で新規作成し、深さ・ゲーム上限の残り手数を区別する。履歴の最大出現数＋探索深さが4未満と証明できるノードだけ履歴を省略し、他は再利用を止めることで、千日手・連続王手の履歴を混同しない。
- **影響**: 固定深さ／ノードでは結果を再現できる。時間はsoft deadlineで1処理分の超過を許し、時間だけの再現性は約束しない。Nativeの単独計測を残すが、Webの難易度はM2のWASM/Workerで決める。R0の仕様・棋譜は維持し、正式な9王採用は別に判断する。全体調査で見つかったR0の検証不足を補強し、生成ループにも指し手数による独立した上限を付けた。結果は [M1検証記録](M1_VALIDATION.md)。
