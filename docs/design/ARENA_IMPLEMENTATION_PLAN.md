2026-11-14 JST。ユーザーの「これでいいので対応する計画を立てて」に基づく。
**U1は承認済み、U2〜U6は実装・公開確認・動画更新まで完了。[進捗](ARENA_IMPLEMENTATION_PROGRESS.md)・[公開確認の根拠と未確認範囲](../ARENA_RELEASE_VALIDATION.md)。以下の目的・ゴールは完了判定に用いた契約として保持する。**

## 目的と採用仕様

対象は将棋を多少指した経験のある人／AI・理系の人。9層の攻防とAI条件を理解して観戦でき、人間対AIにも迷わず入れる画面を作る。
[問題整理](SPECTATOR_UX_REVIEW.md)と[承認モック](ARENA_MOCKUP.md)を基準にする。承認時のHTMLは31,893 bytes、SHA-256 `c3d4fc219a2e12bbf5d5f754d76843de02a2022036c8d16b6b684a67e2d8b3b4`。

- 上部に「AIを観戦」「AIと対戦」。対戦は先後・相手AIを選び、開始する。
- 立体盤は全体把握、2D断面は着手を読むために使う。9層の番号、移動元／先、軌跡を対応させる。
- 盤と主要操作を優先し、設定・モデル条件・研究値は必要時に開く。
- Alpha・PC推奨・スマホ未確認の常時注意書き、送信状態・切替・同意フォームは置かない。対応実績や制限は文書に残す。
- Cloudflareへの棋譜保存は常時有効な自動保存にする。端末への「棋譜保存」は別操作として残す。
- 既存のRust／WASM／Worker／WebGL、Easy／Normal／取得済みSを再利用する。モックの参考棋譜やSVGを、本物の対局・描画・性能として流用しない。

## 計画開始時点（旧UIの履歴）

新画面は操作モックまで。公開中の旧UIにはAI観戦・人間先後・Easy／Normal・Sが実装済み。
保存はschema 1の任意送信で、同意した終局／明示中断を固定本文で1回送る。同じIDの本文変更は409になる。
新UIの実描画と実AI接続、途中snapshotの更新、自動再送は未実装。
旧版の[公開検証](../L6_PUBLIC_VALIDATION.md)と[保存仕様](../GAME_DATA_COLLECTION.md)は履歴として保持する。

## U2：画面構成

`App.tsx`を画面枠・盤・操作・局面詳細・設定シートへ分ける。既存store／controllerを再利用し、公開PRに未接続のモックボタンを残さない。
観戦中は説明を短くして盤と主要操作を画面内へ収める。2Dを主盤にした時の補助断面の重複も解消する。
層選択はI〜IXと元／先を表示し、狭幅では2段配置やシートで44pxを確保する。
2Dの81マスは狭幅で1マス36px以上を目標に実測する。駒がある着地点も太枠で示し、別層の移動元を実在の駒と誤認させない。
AI分析文・思考状態によって盤が毎手ずれないようにする。3Dは遅延ロードし、失敗時も2Dと操作を利用できる。常時カメラ回転はしない。
見た目とDOM順、dialogのfocus復帰、選択状態、手番／王手／終局の通知も確認する。

## U3：対局機能

- 「AIを観戦」はモデル取得なしで1操作で開始。停止中の新しいAI着手と、記録の前後送りを明確に分ける。
- 「AIと対戦」は先後・相手を選んで開始。先手なら人間、後手ならAIから開始。人間の手番だけ駒・持ち駒・合法手・成りを操作できる。
- 設定シートを開いただけでは対局を破棄しない。開始時の置換確認を取り消すと盤・手数・AI条件を保持する。
- AI条件は対局開始時に固定する。対局中に先後・相手・モデルを変更する場合は新規対局にし、保存条件を実際のAIとそろえる。
- 履歴カーソルと対局末尾、進行／停止／終局を分ける。履歴からAIで分岐する場合は別操作で明示し、別IDで保存。通常の端末保存は閲覧位置によらず全手を含める。
- 停止・新規対局・モード／履歴操作・import・投了後に、古いWorker応答を適用しない。
- モデル失敗時は再試行と、別AIで新規対局の入口を出す。無断でAIを切り替えない。モデルID・形式・backend、評価値の視点／尺度、既存の全計測項目を詳細に残す。

## U4：自動保存と移行

現行clientは未同意なら送らず、receiverは同一IDの本文変更を拒否する。UIを消して同意をtrueへ固定するだけでは途中保存に対応しない。
**後方互換の新APIを先に配信し、その後で新clientを接続する。**

### 保存の契機と再送

1. この画面で始めた対局の最初の実着手を保存。閲覧だけ・0手では保存しない。
2. 以降は棋譜に変更がある間、30秒間隔で最新の途中snapshotを保存。各手ごとの通信はせず、1リクエスト実行中は最新の変更をまとめる。
3. 一時停止・終局・投了・新規対局／モード変更の置換では、その時点の末尾を固定して保存。新しい対局の開始を通信待ちにしない。
4. 非表示／離脱時の送信は補助。閉じた瞬間の成功を保証せず、最後に応答確認した途中snapshotを保持済みの基準にする。
5. 失敗時は初回＋最大3回、2秒／8秒／30秒の間隔で同じ送信ID・本文を再試行。期限・上限後もゲームを継続し、送信通知や再送操作を観戦画面へ出さない。

import棋譜は収集しない。履歴の移動も新着手として保存しない。別対局の未送信分を次の対局IDへ混ぜない。

### API・DB・上限

schema 2でgameId・snapshotの単調なversion・送信ID・保存方式の版を識別する。旧版の同意fieldを自動保存へ流用しない。
開始時の先後／AI条件、初期局面・全着手・進行／終局状態とアプリcommitを扱い、表示カーソルを末尾と混同しない。
専用tableまたは明示的なversion分岐で旧schema 1の行・意味・再送を保持する。

- 新規は1対局1行、以降は最新snapshotへ原子的に更新。正規化した検査済み本文でhash計算する。
- 同version・同hashの再送は同じ結果を返し、同version・別本文は競合として拒否。古いversionで巻き戻さず、終局済みを途中状態へ戻さない。
- 着手列の延長を検査し、分岐・AI条件変更は別gameIdで扱う。
- 1件256KiB／2,048着手、日次新規1,000対局・保持本文100MiB・30日保持を基準に維持。UPDATE時の容量差分も同一トランザクションで計上する。
- 初期上限は途中更新128回＋終局更新1回／対局、全更新合計で日次10,000回。同一内容の再送と古いversionは更新回数を増やさない。境界値とD1使用量を検証する。無料枠や共有残量を保証せず、上限時も対局は止めない。
- `received_unverified`を維持。全手合法・学習教師の品質を受信成功から主張しない。期限削除と管理者の停止／復旧を新tableでも確認する。

保存項目は棋譜・開始時AI条件等に限定。名前・メール・生IP／User-AgentのDB列・モデル本体・token・ファイルpathは追加しない。
privacy文書と運用手順を自動保存へ更新し、旧説明との不一致を残さない。ゲーム画面に送信状態やフォームを戻さない。
新規／途中／終局、再送、競合、順序逆転、古い終局前応答、履歴、分岐、AI条件変更、import除外、通信／DB障害、サイズ・件数・更新・容量・保持の境界を検査する。
実D1には自分の合成テスト対局だけを保存し、応答・本文・hash・更新件数を照合後、検証行だけを削除する。

## U5：検証と公開

独立した固定棋譜・手計算の座標でテストをREDから実装し、代表的なバグの注入で検出を確認する。
Macは編集・軽量な静的／単体確認のみ。WebGL・探索・実モデル・重いE2E・録画／エンコードはLinux CIへ置く。
3サイズで初回・観戦中・停止／履歴・人間先手／後手・終局を検査。人間先後×Easy／Normalの4経路、同層／異層、持ち駒、成り、取消、モデル失敗と復帰、全棋譜保存を確認する。
既存Sの対応形式と配布hashを保ち、未対応backend・未確認の端末を成功と数えない。

Claude Codeへ新UIの実画像と差分を渡す。ソース・画像・実操作の確認範囲を分ける。撮影／接続の拒否を反復・迂回せず、ページ限定接続またはCI画像を使い、実機の未確認は残す。
PRでは関連する短い検証、mainでは既存の深い検証を使う。必須8件・関連CI全成功、最新main、重大CodeQL指摘0を確認し、保護を維持して通常mergeする。
CI取得は最短10分間隔。文書のみで重い検証を増やさない。mainで自動公開されるため、U2から実機能を維持した完成単位にする。
U5では統合版のbuild-info・実配信bytes・公開E2E・実D1を改めて固定する。

## U6：動画更新

新UIの公開commitを固定して収録。0秒から明るい9層盤と「将棋、9層にした。」、3秒以内に層をまたぐ実際の駒を大きく見せる。
移動元・先と軌跡、無音字幕、最後のURLを読みやすくする。7〜11秒の実操作も拡大し、履歴送りと新しいAI着手を混同させない。
既存Linuxハーネスで15秒本編・3秒2案・ポスター／OGPを制作。1080×1350／H.264／yuv420p／30fps、尺・全編デコード・実棋譜のRust再生・全hash・公開版一致を確認する。
OGPを公開アセットへ更新する場合は候補画像を先に配信し、その最終公開SHAから動画を生成する。後続の確認記録は文書だけで更新し、不要な再デプロイで動画との版をずらさない。
実装していない演出・AIの強さ・拡散の実績を主張しない。X投稿は別の送信依頼を受けてから行う。
