2026-10-28。ユーザー指示によりM4本生成と併せて実施する。**変換器を準備中。実棋譜の全手再生はまだ未実施。** ルールは[標準1王](RULESET.md)、完了条件は[ROADMAP](ROADMAP.md#m5-将棋ったー棋譜との互換性検証)。

## 目的とゴール

現行ルール版の実際の棋譜を空でない固定集合として取得し、全着手・各局面の盤面と持ち駒・終局結果をRustで照合する。対象の全件成功、出所・日時・ルール版・件数・hash・不一致への対応をRULESET §9へ記録してM5完了とする。選択した棋譜の一致を、将棋ったー全体の完全互換へ一般化しない。

## 手順と実行場所

1. `training.shogitter`で公開ページのJSON参照形式を独立に読み、ルールIDと対象IDを確認する。サイトのJavaScriptは実行せず、第三者のエンジンコードをコピーしない。
2. 原本の最終盤と着手差分を逆再生し、標準初期配置と一致するか確認する。筋と9×9を直列化した段を、3Dの筋・段・層へ変換する。移動・成り・捕獲・打ちと持ち駒差分を検証する。
3. Rustへ全手を順番に適用し、各局面の盤面・持ち駒と原本差分を照合する。最後に元の持ち駒集計、投了側・勝者・順位、Rustの棋譜再生と結果を照合する。
4. 原本HTMLと変換中の情報は外部Linuxのgitignore対象`runs/m5/`だけに置く。全対象を取得してから再生し、失敗しても対象集合を変更しない。公開するのはURL・日時・原本／record hash・着手数・集計・終局・最終hash・不一致の概要だけ。棋譜本体をGit・HF・公開artifactへ入れず、学習へ使用しない。
5. 通常PRは手作りのプロトコル例・独立期待値・変異検出を検証する。実棋譜は、CIの`workflow_dispatch`で`m5_live=true`を明示したLinux実行だけで取得する。Macでは実棋譜の再生や重い検証をしない。サイト接続に失敗した場合は成功扱いにせず、同じ対象を承認済み外部Linuxで検証する。

```bash
# ghの操作は制御側。実棋譜の取得・再生はLinux runnerで行う。
gh workflow run ci.yml --ref <検証済みの対象ブランチまたはmain> -f m5_live=true
```

実行結果はPythonジョブの専用ステップに集計JSONとして残す。通常CI・明示実棋譜検証・公開後E2Eを区別し、実行したcommitと結果を固定記録にする。M4の生成は、M5でルールに不一致が見つかった場合の調査・対応後に開始する。
